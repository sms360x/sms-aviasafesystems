## 2. SET LOCAL ROLE

Single transaction:

```sql
BEGIN;
SELECT current_user;              -- postgres
SET LOCAL ROLE authenticated;
SELECT current_user;              -- authenticated
SELECT session_user;              -- postgres
COMMIT;
```

Observed:

    before:                                 ('postgres', 'postgres')
    after SET LOCAL ROLE authenticated:     ('authenticated', 'postgres')

Reset check, new transaction on the same connection:

    new transaction current_user/session_user: ('postgres', 'postgres')

**Result: PASS.** `current_user` becomes `authenticated` inside the transaction;
`session_user` stays `postgres`; the role is reset to `postgres` in the next
transaction. `SET LOCAL ROLE` is transaction-scoped and does not leak.

## 3. SET LOCAL session variables

Single transaction:

```sql
BEGIN;
SELECT set_config('app.current_tenant', 'some-uuid', true);
SELECT set_config('app.current_role', 'TENANT_ADMIN', true);
SELECT current_setting('app.current_tenant', true);
SELECT current_setting('app.current_role', true);
COMMIT;
```

Observed:

    inside tx:      ('some-uuid', 'TENANT_ADMIN')

Reset check, new transaction on the same connection:

    new transaction: ('', '')

**Result: PASS.** Both variables take effect for the transaction and are cleared
when it ends. (The post-reset value is the empty string, not NULL — see §6.1.)

## 5. RLS enforcement test

A temporary policy was created **inside a transaction and rolled back** (it must
not persist). Table: `public.hazards` (214 rows; top tenant
`5a8cedc3-8151-5c9a-89fd-5ed101191ba9` has 170 rows).

```sql
BEGIN;
CREATE POLICY test_rls_check_2c2 ON public.hazards
    FOR SELECT TO authenticated
    USING (tenant_id::text = current_setting('app.current_tenant', true));

SET LOCAL ROLE authenticated;
SELECT set_config('app.current_tenant',
                  '5a8cedc3-8151-5c9a-89fd-5ed101191ba9', true);

SELECT COUNT(*) FROM public.hazards;          -- tenant A only

SELECT set_config('app.current_tenant',
                  'ffffffff-ffff-ffff-ffff-ffffffffffff', true);
SELECT COUNT(*) FROM public.hazards;          -- non-existent tenant

ROLLBACK;
```

Observed:

    SET ROLE authenticated + tenant A GUC -> hazards count: 170  (total 214)
    GUC set to a non-existent tenant      -> hazards count: 0
    test policy rows after rollback: 0

**Result: PASS.** With `SET LOCAL ROLE authenticated` and the tenant GUC set to
tenant A, the query returned **170 of 214** rows (tenant A only). A GUC pointing
at a non-existent tenant returned **0**. The temporary policy was removed by the
rollback (0 rows in `pg_policies`). Tenant isolation is enforced by the policy
under the `authenticated` role.

### 6.1 Hardening note for 2C.3 (implementation detail, not a D7/D8 change)

An **unset** `app.*` GUC reads as the **empty string**, not NULL — even on a
fresh connection (observed `current_setting('app.current_tenant', true)` →
`''`). A bare `current_setting('app.current_tenant')::uuid` would therefore raise
`invalid input syntax for type uuid: ""` (an error → 500) whenever the GUC is
missing, instead of denying.

Recommended in the policy implementation: guard the cast, e.g.

```sql
NULLIF(current_setting('app.current_tenant', true), '')::uuid
```

so a missing/unset value evaluates to NULL (fail-closed → no rows), not an
error. The app will set the GUC in every transaction, so this is
defence-in-depth; but the template should carry the guard. The SME-approved
predicates in `2C.1_rls_design.md` §11 remain the design of record; this note is
the concrete cast-safety requirement for 2C.3.
