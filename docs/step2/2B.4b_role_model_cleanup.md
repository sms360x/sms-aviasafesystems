### 2. `CUSTODIAN_ROLES` and `REPORT_VIEWER_ROLES` are different rules

The prior instruction assumed all three role sets governed raw VSR access. That
is not correct:

- `_RAW_VSR_ROLES` and `CUSTODIAN_ROLES` govern raw VSR / reporter identity.
- `REPORT_VIEWER_ROLES` governs register-**row** visibility (a different rule).

In 2B.4b: the distinction is reported; `REPORT_VIEWER_ROLES` was **not**
collapsed into the raw-VSR rule. `_RAW_VSR_ROLES` / `CUSTODIAN_ROLES` were
**not** collapsed either — the call sites (`get_report`, `get_reports`,
`can_view_reporter_identity`) do not all carry the tenant context needed to
express the corrected rule, so the collapse is deferred.

### 3. `SUPER_ADMIN` in `CUSTODIAN_ROLES`

`CUSTODIAN_ROLES = {TENANT_ADMIN, AIRLINE_ADMIN, SUPER_ADMIN}`. Under the
corrected raw-VSR rule (1C.1 + correction) the rule is: `TENANT_ADMIN` or the
**Safety Department OFFICER**. `SUPER_ADMIN` is not an operator user; removing
it from the raw-VSR rule is deliberate and is deferred to the item that collapses
the sets.

### 4. `can_view_reporter_identity` signature

`can_view_reporter_identity(report, user)` has no tenant document from which to
read `safety_department_name`. The confidential-service rule needs the tenant
(to identify the Safety Department). The signature change is required before the
rule can be expressed; not implemented here because it touches callers.

### 5. `CROSS_TENANT_ROLES` retains the legacy `CAAN_SMD` member

See Part 3.2. Retained because ~40 out-of-scope readers still compare the
literal `"CAAN_SMD"`; canonicalizing the list alone would make `STATE_SMD`
inconsistent (passes the list gate, fails the literal checks). Reported under
STOP condition #1.

### 6. `ROLE_DEFAULT_REGISTRATION = "AIRLINE_ADMIN"`

Registration still writes the legacy value and embeds it in the register
response; `ROLE_SAFETY_OFFICER` / `ROLE_SAG_MEMBER` and the `services/invites.py`
role matrix still carry the legacy/dual-accept vocabulary. Migrated with
`services/invites.py` in a later item.

### 7. `routes/admin.py:891` response fallback

The updated-user response falls back to `req.role or "USER"`; `"USER"` is a
legacy role name. Left unchanged (display-only fallback, no write).
