### 2.2 `ROLE_DEFAULT`

`ROLE_DEFAULT` changed from `"USER"` to `"STAFF"` (`config.py:173`).

Verified:

```
settings.CANONICAL_ROLES == ['SUPER_ADMIN','STATE_SMD','TENANT_ADMIN',
                             'DEPT_ADMIN','OFFICER','ACCOUNTABLE_EXECUTIVE',
                             'STAFF']
settings.ROLE_DEFAULT == 'STAFF'
```

(Note: the item's verify snippet `from app.core.config import CANONICAL_ROLES`
does not work — the constants are attributes of the `settings` instance, not
module-level names. Verified via `from app.core.config import settings`.)

### 2.3 Effect of `ROLE_DEFAULT`

`ROLE_DEFAULT` is the fallback assigned by the join-team flow
(`services/tenant_registration.py:571,587`), and a token fallback
(`middleware/auth.py:150`, `middleware/rbac_middleware.py:86`). Both `USER` and
`STAFF` normalize to `employee` for the module gate, so the change is
least-privilege-equivalent; the only observable change is the stored literal
for new legacy-code joiners (`USER` → `STAFF`). That is the intended direction
of the 2B.3 `USER → STAFF` migration.

## 3. Schema change

### 3.1 Migration

`supabase/migrations/20261012130000_tenants_safety_department.sql` (idempotent):

```sql
ALTER TABLE public.tenants
  ADD COLUMN IF NOT EXISTS safety_department_name text NULL;

COMMENT ON COLUMN public.tenants.safety_department_name IS
  'Tenant-specific Safety Department name. Used for the department-based raw VSR rule (Q6). NULL means the tenant has no department-based VSR access; only TENANT_ADMIN gets it.';
```
