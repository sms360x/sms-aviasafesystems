# Phase 2A — Membership Model Design

Status: SME-approved 2026-10-10. This is the Phase 2A design of record.
(Read-only design pass — no code, no schema, no migrations.)
DATE: 2026-10-10
BRANCH: step2-governance
ITEM: 2A.1 (Step 2 plan W1)

> Correction (2026-10-12): The original design permitted
> multi-membership per user. SME review on 2026-10-12
> established the ICAO rule — one user, one tenant, one
> role — and repurposed the memberships table as the
> Super-Admin reporting substrate. The auth boundary
> reads from the users row. See 2A.5 evidence doc for
> the implementation.

This document is the design for replacing the single `role`/`tenant_id`
string on a user with effective-dated memberships (plan decisions D3, D15).
It reports the census of the current model, proposes the table and the
compatibility path, and lists risks and open questions. It contains no code.

---

## 1. Current state (census)

- Identity: **Firebase Auth** (ID tokens). The auth boundary is
  `backend/app/middleware/auth.py`.
- Membership: a single row per user in the `users` table
  (`UserProfile`, `backend/app/db/db_models.py`). There is **no**
  memberships table anywhere in the backend (verified: zero matches for
  `membership`/`memberships` table usage).
- `users.tenant_id` is a **uuid** (`uuid5('tenant:' + slug)`), while the
  request user dict carries the **slug**. `backend/app/db/ids.py`
  (`tenant_uuid`/`register_tenant`/`tenant_slug`) maps between them.

### 2.3 Interpreting the counts
The two totals (131 role, 250 tenant) are the blast radius of the
auth-boundary change, not 381 independent edits: almost all read the
**user dict** the boundary produces. If the boundary still returns a dict
with `role` and `tenant_id` keys (now sourced from the active
membership), the vast majority of call sites need **no change**. The
work is concentrated in the boundary, the user-write paths
(`admin.py`, `tenant_credentials.py`, `users.py`, `invites.py`), and the
role-model unification (W2).

## 3. The auth boundary as it exists today

File: `backend/app/middleware/auth.py`.

- `resolve_user_context(email, role, tenant_id)` (`:60`) normalises and
  returns `{"role": ..., "tenant_id": ...}`:
  - `_ROLE_CLAIM_ALIASES = {"STATE_SMD": "CAAN_SMD"}` (`:57`) rewrites
    `STATE_SMD` → `CAAN_SMD` (the *inward* normalisation Step 2 reverses, D4).
  - `tenant_id` underscores are rewritten to hyphens (`:65-68`).
  - If the role is the default and no tenant is present, it falls back to
    a **tenants-table email lookup** (`_lookup_tenant_by_email`, `:28`) then
    an **email-domain → tenant slug map** (`get_tenant_slug_from_email`,
    `:80`), which assign `AIRLINE_ADMIN` + a slug.
- `get_current_user` (`:120`) verifies the Firebase ID token
  (`verify_firebase_token`, `check_revoked=True`), reads
  `email`/`role`/`tenant_id`/`department` from the claims, calls
  `resolve_user_context`, rejects a SUSPENDED tenant (`_tenant_is_suspended`,
  `:95`; fail-open), and returns the user dict:
  `{uid, email, role, tenant_id, department, claims:{role,tenant_id,department}}`.
- The user dict is **not cached and not stored on the request**. There is no
  `request.state.user` assignment in production code — only
  `core/logging.py:48` *reads* `request.state.user` if present (it is
  present only in tests), and `rbac_middleware._user_from_request` (`:68`)
  reads it or independently re-verifies the Bearer token.
- Dependency shims built on the dict: `get_tenant_user` (`:158`),
  `get_caan_user` (`:169`), `get_admin_user` (`:180`),
  `get_safety_manager` (`:191`), `get_accountable_executive` (`:254`,
  the known mis-gate from 1C.2), `get_responsible_manager` (`:232`),
  `get_department_scope` (`:218`).

**Assessment vs the Step 2 plan:** consistent. The plan describes a single
role + tenant on the user, resolved at the auth boundary, with no
effective-dated memberships. The one material addition is that the
boundary is invoked **twice per request** for gated paths
(`get_current_user` in the route and `rbac_middleware`), so any new
membership resolution must be deterministic and cheap (or cached).

### 3.1 Where the user dict is passed to services

`user: Dict` / `user: dict` appears in **364** function signatures across
`backend/app`. Services and route helpers receive the request user dict
and read `user["role"]` / `user["tenant_id"]` (e.g.
`ReportService.get_reports(user)`, `CanCapService.ae_decide(..., user)`,
`SramService` accept paths, `master_register`, dashboard services). In a
few places the role/tenant is copied into a local variable early
(e.g. `role = (user or {}).get("role")`) and used later in the same
function — these are local reads of the same dict and are served
unchanged by a dict-shaped boundary.

## 4. Proposed memberships table

```
memberships
  id              uuid         PK
  user_id         uuid         FK users.id, NOT NULL, indexed
  tenant_id       uuid         FK tenants.id, NULL   -- NULL = platform (SUPER_ADMIN)
  role            text         NOT NULL
  effective_from  timestamptz  NOT NULL
  effective_to    timestamptz  NULL          -- NULL = open-ended
  is_active       boolean      NOT NULL DEFAULT true
  created_at      timestamptz  NOT NULL
  updated_at      timestamptz  NOT NULL
```

Indexes / constraints:
- `ix_memberships_user_from` on `(user_id, effective_from DESC)`.
- `ix_memberships_user_active` on `(user_id) WHERE is_active`.
- Partial unique: `ux_memberships_user_tenant_role_active` on
  `(user_id, tenant_id, role) WHERE is_active AND effective_to IS NULL` —
  prevents duplicate concurrent memberships for the same scope; **does not**
  force one row per user.
- `tenant_id` is a **uuid** (FK), consistent with `users.tenant_id`;
  the slug→uuid conversion stays at the boundary via `db/ids.py`.
- **No `department` column** on the membership (SME Q1 = (a), 2026-10-10):
  one email = one user = one tenant, so department stays on
  `users.department`.

Companion table — `oversight_relationships` (SME Q2 = yes; added in 2A.2):

```
oversight_relationships
  id                    uuid         PK
  regulator_tenant_id   uuid         FK tenants.id, NOT NULL
  operator_tenant_id    uuid         FK tenants.id, NOT NULL
  effective_from        timestamptz  NOT NULL
  effective_to          timestamptz  NULL
  created_at            timestamptz  NOT NULL
```

Indexes / constraints:
- Partial unique: `ux_oversight_regulator_operator_active` on
  `(regulator_tenant_id, operator_tenant_id) WHERE effective_to IS NULL`.
- Index on `(regulator_tenant_id)` and on `(operator_tenant_id)`.

This models D15/L9 (one airline, multiple regulators) as a
**tenant↔tenant** relationship.

Justification against the decisions:
- **D3 (effective-dated membership):** `effective_from`/`effective_to` +
  `is_active` give a date-bounded membership; "single active context" is a
  **request-time resolution rule** (§6), not a one-row-per-user table rule,
  because a user may legitimately hold several memberships over time and
  across tenants.
- **D15 (one-to-many oversight):** the user↔tenant↔role rows model a user
  in several tenants. The **tenant↔tenant** oversight relationship (one
  operator reporting to one-or-many regulators, L9) is *not* a membership
  row; it is the companion `oversight_relationships` table defined above
  (SME Q2 = yes, 2026-10-10).
- **L9 (multi-state regulator):** modelled by multiple `STATE_SMD`
  memberships (a state user is a member of the regulator tenant) plus
  multiple oversight relationships; no future migration needed if the
  relationship table is created now.

No column is added to `users` in this design; `users.role`/`users.tenant_id`
are retained during the compatibility window (§5) and retired per D6/W2.

### Boundary shape after 2A

The auth boundary will compose the request user dict from two sources:

- `users` row: `uid`, `email`, `department`, `is_developer`
- active membership: `role`, `tenant_id`

The dict shape is unchanged from today. No downstream reader (role or
tenant) needs modification. Evidence: 2A.1 census (131 role reads, 250
tenant reads).

## 5. Compatibility path

The product must keep working during Phase 2A. Recommended approach:
**resolver-with-fallback, gated by a feature flag; backfill as a shadow
copy; remove the twin read after 2A.5.**

- Add `resolve_active_membership(user)` at the auth boundary:
  1. Resolve `users.id` from the verified `uid` (then `email`).
  2. Load active memberships (`is_active` AND (`effective_to IS NULL` OR
     `effective_to > now`)).
  3. If one is found, the active context is `{role, tenant_id}` from the
     membership (department continues to come from `users.department`).
  4. If none is found, **fall back** to the legacy `users.role` /
     `users.tenant_id` (+ `department`).
- Gate step 2–3 behind a config flag `MEMBERSHIP_MODEL_ENABLED`
  (`backend/app/core/config.py`), default **false** during 2A.2–2A.3 so
  behaviour is unchanged until the backfill is verified.
- During 2A.3 the backfill **shadow-writes** one membership per existing
  user from `users.role`/`users.tenant_id`; after verification, 2A.4 flips
  the flag on and parity is asserted (2A.5).
- The fallback is explicitly **temporary**: it is removed in W2 when
  `users.role` is retired (D6). This avoids the compatibility path becoming
  permanent (a listed risk).

Why this approach: it needs no dual-write on every request, keeps the
existing `user` dict shape (so the 381 read sites are unaffected), and the
flag gives an instant rollback without a deploy of new code paths.

## 6. Corrected design (2026-10-12)

The original design permitted multiple memberships per
user. SME review corrected this:

    - One user = one tenant = one role.
    - A person acting for two organisations has two
      separate user records in the application.
    - The auth boundary reads from the users row.
    - The memberships table is retained as the
      Super-Admin reporting substrate.

### Purpose of the memberships table

It is the reference layer for the Super-Admin dashboard.
It holds one active row per user, recording the
(user, tenant, role) relationship. The dashboard queries
it to produce cross-tenant reports that the Super Admin
sends to tenants.

The table is not a source of truth. It is derived.

### Sync

The table is kept in sync when users are created
(ensure_membership) or their role changes
(update_membership_role).

### Not in scope

The Super-Admin dashboard itself is a later item. The
schema is ready for it. This item does not build the
dashboard.

## 8. Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Backfill produces more memberships than expected (duplicate rows) | Medium | Medium | Partial unique constraint (§4); reconciliation count before/after; idempotent upsert keyed on `(user_id, tenant_id, role, effective_from)`. |
| Active-context resolution returns a different answer than the current single role | Medium | High | Parity tests (2A.5) comparing resolver vs legacy across the live user set; enable flag only after parity is green. |
| Cross-tenant (regulator) users at backfill | Medium | High | Backfill `STATE_SMD`/`CAAN_SMD`/`SUPER_ADMIN` as tenantless (or regulator-tenant) memberships; assert the resolver still marks them cross-tenant; keep `CROSS_TENANT_ROLES` behaviour until W2. |
| Users with **no** membership after backfill | Medium | Medium | Explicit fallback to `users.role` during the window; a reconciliation query lists users with zero memberships before enabling. |
| Deactivated users | Low | Medium | There is **no `users.is_active`** today; deactivation is Firebase `disabled` (auth-level) and tenant `SUSPENDED`. **SME Q4 = leave as is** — no new column; membership `is_active` is a scheduling flag only. |
| Compatibility path becomes permanent | Medium | Medium | The fallback is scoped to Phase 2A only and is removed in W2 when `users.role` is retired (D6); tracked as an exit criterion. |
| Boundary is invoked twice per request (route + middleware) | Low | Medium | Deterministic rule (§6) + optional short-TTL cache of the resolved context keyed by uid; the resolver reads are indexed and small. |
| Slug/uuid mismatch during migration | Low | High | Keep slug↔uuid conversion in `db/ids.py`; membership.tenant_id stored as uuid; parity test asserts `tenant_slug(membership.tenant_id)` equals the legacy slug. |

## 9. Open questions for SME — resolved 2026-10-10

All seven questions from the design pass were answered by the SME on
2026-10-10.

- **Q1 — Department on membership or user?** **ANSWER: (a) on the user.**
  Rationale (SME, 2026-10-10): a user has one email and cannot login to
  another tenant; the operational model is one email = one user = one
  tenant. Department stays on `users.department`; the memberships table
  does not carry a department column.
- **Q2 — Companion `oversight_relationships` table?** **ANSWER: yes.** Add
  `oversight_relationships` (regulator_tenant_id, operator_tenant_id,
  effective_from, effective_to) in 2A.2 alongside `memberships`. Required
  for D15/L9 (one airline, multiple regulators).
- **Q3 — `is_developer` placement?** **ANSWER: keep on user.**
  `is_developer` (and `SUPER_ADMIN`) are platform-level markers, not
  tenant-scoped.
- **Q4 — Deactivation semantics?** **ANSWER: (a) leave as is.**
  Deactivation is handled by Firebase user disable and tenant `SUSPENDED`.
  No new column. No change to the current mechanism.
- **Q5 — SUPER_ADMIN representation?** **ANSWER: (b) membership with
  `tenant_id = NULL`.** The auth boundary treats "membership with NULL
  tenant + role SUPER_ADMIN" as the platform context. No special case.
- **Q6 — Email-fallback survival?** **ANSWER: (c) keep and deprecate.**
  Add a warning log when the fallback fires; remove in Step 3 once the log
  confirms no users depend on it.
- **Q7 — Keep exposing the slug as `tenant_id`?** **ANSWER: retain.** The
  user dict keeps the slug as `tenant_id` at the boundary; the database
  stores the uuid. This mismatch is documented, retained as-is for now,
  and flagged for Step 3 cleanup.
