## 1. The canonical department list (if it exists)

There is **no `departments` table** and **no typed `tenants.department` column**.
A canonical list exists only as a **derived, classification-scoped code list** in
code, and is stored per tenant as a document key.

### 1.1 Primary source — `OperationalScope.departments`

`backend/app/models/tenant_profile.py:15-58` — `OperationalScope` (a fixed
`str, Enum`) maps each tenant classification to its applicable **department
codes**:

| Classification | `departments` (codes) |
|---|---|
| `AIRLINE_FIXED_WING` | `["safety","flight_ops","camo","qa"]` |
| `AIRLINE_ROTARY` | `["safety","flight_ops","camo","qa"]` |
| `AMO` | `["safety","maintenance_145","qa"]` |
| `AERODROME` | `["safety","airside_ops","arff"]` |
| `GROUND_HANDLING` | `["safety","ground_ops","qa"]` |
| `REGULATOR` | `["safety","smd","fssd","assd"]` |

`TenantOperationalProfile.applicable_departments` is derived from `scope` in the
model validator (`tenant_profile.py:101-113`). Eleven distinct codes exist
across the six scopes; `safety` is universal.

### 1.2 Labels — `DEPARTMENT_LABELS`

`backend/app/services/tenant_registration.py:82-91`:

```
"safety" -> "Safety"        "flight_ops"   -> "Flight Operations"
"camo"   -> "CAMO"          "maintenance_145" -> "Part-145"
"qa"     -> "QA"            "airside_ops"  -> "Airside Operations"
"arff"   -> "ARFF (Rescue & Firefighting)"  "ground_ops" -> "Ground Operations"
```

Only **8** of the 11 scope codes have a label; the regulator codes `smd`,
`fssd`, `assd` fall back to the raw code (`tenant-lookup`:
`DEPARTMENT_LABELS.get(d, d)`).

### 1.3 Register alias table — `master_register._DEPARTMENT_ALIASES`

`backend/app/services/master_register.py:41-70` holds a separate spelling map
used by `normalize_department()` for register filtering (e.g. `"145"` /
`"maintenance_145"` / `"maintenance"` / `"amo"` → `"Part-145"`; `"flight ops"` /
`"ops"` / `"line pilot"` → `"Flight Operations"`; `"qa"` / `"smd"` / `"safety"`
→ `"Safety"`; `"cabin crew"` → `"Cabin Services"`). Note `qa` and `smd` both
normalize to `"Safety"` here.

### 1.4 Frontend resolver — `public/js/department_resolver.js`

`department_resolver.js:19-113` holds **yet another** map
(`DEPARTMENT_BY_PREFIX` + `PREFIX_BY_CLASSIFICATION`) of email-prefix →
department **label**, scoped by classification. Its labels differ from
`DEPARTMENT_LABELS`, e.g. `"145"` → `"Maintenance Department (Part-145)"`,
`"camo"` → `"CAMO / Technical Services"`, `"safety"` → `"Corporate Safety
Department"`, `"smd"` → `"CAAN - Safety Management Department (SMD)"`, default →
`"Operational Safety Unit"`.

### 1.5 Where the tenant's list is stored

On the tenant document as `applicable_departments` (a list of codes), set at
registration (`tenant_registration.py:378,405`) and returned by
`/api/v1/auth/tenant-lookup`. It is not a typed column (it lives in the tenant
JSONB `data` bag; the `Tenant` ORM model has no such column).

## 2. The `join.html` dropdown source

- `public/join.html:306-331` `loadDepartments(code)` fetches
  `GET /api/v1/auth/tenant-lookup?code=...` and renders one `<option>` per
  `data.applicable_departments` item.
- Backend: `backend/app/routes/auth.py:428-460` `tenant_lookup_endpoint` →
  `resolve_tenant(code, tenant_id)` → `tenant_doc.get("applicable_departments")`
  → returns `[{"code": d, "label": DEPARTMENT_LABELS.get(d, d)}]` (`:457-459`).
- So the source is **`OperationalScope.departments`**, reached via the tenant
  document's `applicable_departments`; the item shape is
  `{ "code": "<code>", "label": "<label>" }`.
- `join.html` overrides three labels locally (`join.html:218-222` `DEPT_LABELS`:
  `flight_ops` → "Flight Operations", `maintenance_145` → "Engineering &
  Maintenance (Part-145)", `ground_ops` → "Ground Handling / Ramp").
- The form payload sends `department: <code>` (`join.html:441-450`).
- Backend `join_team` (`tenant_registration.py:560-661`) validates the code
  against `applicable_departments` (`:601-606`) and stores the **label**
  (`label = DEPARTMENT_LABELS.get(code, code)`, `:608`) into the user's
  `department` claim and `users.department` (`:618,627`). So **codes go in,
  labels are stored** on the user.

`/api/v1/auth/verify-invite` and `/api/v1/auth/join-team` are the other join
endpoints (`routes/auth.py:389-407`).

## 3. The tenant's department concept

- No `departments` / `tenant_departments` table exists.
- No typed `tenants` column holds a department list; `applicable_departments` is
  a document key (JSONB), derived from the classification.
- The list is **classification-driven** (`OperationalScope`): airlines get
  safety/flight_ops/camo/qa; AMOs maintenance_145/qa; aerodromes
  airside_ops/arff; ground-handling ground_ops/qa; regulators smd/fssd/assd.
- `tenants.safety_department_name` (added 2B.2) is a single free-text Safety
  Department **name**, not the list, and is not yet populated or used.

## 6. How the hazard register uses department

- **Normalization:** `master_register.normalize_department()`
  (`master_register.py:65-70`) canonicalizes via `_DEPARTMENT_ALIASES`
  (`:43-62`) — the many-spelling reconciliation.
- **Master register / unified register** (`master_register.py`):
  - DB `WHERE department` when a filter is given (`:199-204`, `:356`, `:436`,
    `:450-451`).
  - Python `_match_department()` on each row (`:275-278`), used to skip hazards
    (`:400-402`).
  - Assignee/department scoping: `user_department` compared after
    `normalize_department` (`:289`); single assignee → `where("department" ==
    user_department)` (`:450-451`).
- **Route-level department filters:**
  - `routes/hazards.py:277,306-307` — `?department=` on the hazard list.
  - `routes/dashboard.py:201-275` — `department` / `user_department` params;
    department-scoped accounts are forced to their own department (`:230-237`).
  - `routes/can_cap.py:58-142,285-303` — CAN/CAP list + department isolation;
    `can_cap_service.py:834-837,1148-1193` — CAN/CAP `department` filter/stats.
- **Hazard/CAN/CAP fields:** hazards carry a `department` field
  (`models/hazard.py:236,283,325,355`); CAN/CAP models carry `department`
  (`models/can_cap.py:203-297`). Hazard reference function code is derived from
  department (`models/hazard.py:58-69`, `HazardFunctionCode` OPS/ENG/CAB/MNT/…).
- **`concerned_department`:** a column exists (`db_models.py:1476`) and appears
  in `models/risk_register.py:36,54,75`, but **no code filters or reads it** —
  it is stored-only.

Segregation therefore depends on the department **string matching** after
`normalize_department`, which is why the alias table exists.

## 7. Email ↔ department connections

Email prefix is assumed to map to department in several places:

- `backend/app/middleware/auth.py:227-245` — `DEPARTMENT_SCOPE_PREFIXES =
  {"145":"Part-145","camo":"CAMO","ops":"Flight Operations"}` and
  `get_department_scope(user)` keys off `email.startswith(prefix)`. Used to force
  a department scope (read-only to that department) in
  `routes/dashboard.py:230-237` and `routes/can_cap.py:85,99,140,298`.
- `backend/app/routes/occurrence_reports.py:45-54` — `can_submit_mor` uses the
  email local-part as a fallback (`camo`/`qa`) in addition to a role list.
- `public/js/department_resolver.js` — the frontend derives the displayed
  department and `X-User-Department` from the email prefix, per classification
  (§1.4).
- Seed conventions: demo accounts are provisioned with emails like
  `safety@`, `camo@`, `145@`, `ops@` (`backend/seed/**`), and
  `master_register._DEPARTMENT_ALIASES` includes persona tokens
  (`"line pilot"`, `"cabin crew"`).

So yes — email prefix (local-part) is treated as a department signal in the auth
scope helper, the MOR-submit rule, the frontend resolver, and the seeders.

## 8. Findings and implications for 2B.4

### 8.1 Does a canonical list exist?

**Yes, but only as a derived code list**, not as a single source of truth. The
origin is `OperationalScope.departments` (classification-driven); it is surfaced
per tenant as `applicable_departments` and labelled (partially) by
`DEPARTMENT_LABELS`.

### 8.2 If yes: where, and how consistent is it?

It is spread across **four** places that disagree:

1. `OperationalScope.departments` — 11 codes (`models/tenant_profile.py`).
2. `DEPARTMENT_LABELS` — 8 labels, missing `smd`/`fssd`/`assd`
   (`services/tenant_registration.py`).
3. `master_register._DEPARTMENT_ALIASES` — register normalization, where `qa`
   and `smd` collapse to `"Safety"` (`services/master_register.py`).
4. `department_resolver.js` `PREFIX_BY_CLASSIFICATION` — a different label set
   per classification (`public/js/department_resolver.js`).

Plus `join.html` locally overrides three labels, and `survey/index.html`
hardcodes a fifth, unrelated list. Stored data reflects the drift:
`users.department` mixes codes-adjacent labels and full names (§4), and
`join_team` stores labels while invites store codes.

### 8.3 If no: what must be added?

Not applicable — a list exists. (The gap is unification, not creation.)

### 8.4 Which forms need to be aligned?

- `step3-manage.html` Create/Edit User — free-text; should use the list.
- `step1-regulator.html` Admin Department — free-text.
- `admin/psoe-audit.html`, `psoe-audit.html`, `can_cap/issue.html`,
  `dashboard/master-register.html` filter — free-text.
- `survey/index.html` — a hardcoded third label set.
- `join.html` / `settings/team.html` — already list-driven (codes), but with a
  local label override.

### 8.5 Does the hazard register segregation depend on a consistent department value?

**Yes.** `master_register` filters and matches on `normalize_department(...)`,
so it relies on the alias table to reconcile code/label/variant spellings. Any
new canonical value must normalize to the same token the register stores on
hazards/CANs/CAPs, or rows silently drop out of a department-filtered view.

### 8.6 What is the smallest correct change?

The factual minimal touchpoints for a consistent value are: (a) reduce the four
disagreeing lists to one source (code + label), (b) bind the free-text
department fields to it, and (c) decide code-vs-label as the stored
`users.department` form (currently labels, while invites store codes). No
design is prescribed here.
