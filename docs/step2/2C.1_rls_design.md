## 3. The application's identity at the request

`backend/app/middleware/auth.py`:

- `get_current_user` verifies the Firebase ID token, then **ignores the token's
  role/tenant** and calls `resolve_user_context(email)`, which reads the
  authoritative `users` row (`UserProfile`): `role`, and `tenant_id` (uuid)
  resolved to the tenant **slug** via `_tenant_slug`. A missing row yields
  `role=None` / `tenant_id=None` and protected endpoints deny.
- The request user dict carries: **`uid`, `email`, `role`, `tenant_id` (slug),
  `department`, `claims`**. `is_developer` is **not** currently placed in the
  dict (it exists on `users.is_developer`).
- The tenant UUID stored in tables is the deterministic
  `uuid5('tenant:' + slug)`; the request carries the **slug**.

At the DB connection level, **none** of this is present today. There is no
session variable, no `SET ROLE`, and no Firebase-JWT path into Postgres. The
only identity a policy can currently read is a GoTrue claim that is never set,
or `app.current_tenant` that nothing sets.

Consequence: before any policy can enforce, the request identity must be
carried to the database **per transaction**. That is D7.

| Item | Value |

| Grants on app tables | `authenticated` holds full DML (`SELECT/INSERT/UPDATE/DELETE/REFERENCES/TRIGGER/TRUNCATE`) on `public` tables, and the default privileges on new `public` tables grant the same; `anon` and `service_role` likewise |

Two facts matter for D8:

1. **`postgres` has `BYPASSRLS`.** Per PostgreSQL, `BYPASSRLS` roles bypass RLS
   **even when a table is `FORCE ROW LEVEL SECURITY`**. So `FORCE RLS` alone
   would **not** gate this connection.
2. A **non-owner, non-BYPASSRLS** role (e.g. `authenticated`, or a new
   dedicated role) makes RLS apply without FORCE; `postgres` is already able to
   `SET ROLE` to `authenticated`.

## 6. Decision D7 — RLS identity model

**Recommendation: Option A — session GUC (`SET LOCAL` / `set_config(..., true)`).**

Per request, at the start of each database transaction, the app sets:

```
SELECT set_config('app.current_tenant',  <tenant uuid>, true),
       set_config('app.current_tenant_slug', <tenant slug>, true),
       set_config('app.current_role',    <canonical role>, true),
       set_config('app.current_user',    <firebase uid>, true),
       set_config('app.current_is_developer', <bool>, true);
```

Policies read `current_setting('app.current_tenant', true)` (with the
missing-ok flag so an unset value yields NULL, not an error) and compare to the
table's tenant column.

Why Option A over Option B (surface the Firebase JWT to Postgres):

- Postgres has no native Firebase JWT decoder; Option B needs the app to decode
  and re-present the claim anyway, which is Option A with extra steps.
- Option A is the standard Postgres pattern and needs no extension.
- It carries only the minimum identity the policies need (tenant/role/uid), not
  a bearer token.

Implementation shape (for 2C.2/2C.3; not built here):

- A request-scoped context (a `ContextVar`) is populated by the auth boundary
  from the `users`-row identity that already exists (`get_current_user`).
- A SQLAlchemy **`after_begin`** listener (on the sync engine behind the async
  engine) executes the `set_config(..., true)` calls once per transaction, on
  both connection paths (`session_scope` and the bridge session). `set_config`
  is parameterised — values never interpolate into SQL.
- The tenant value should be the **uuid** for uuid-typed tables, and the
  **slug** is also set for the text-typed tables and for `tenants` (§11, Q4).

**Pooling note.** Under the transaction pooler a transaction is pinned to one
backend, so `SET LOCAL` / `set_config(..., true)` are transaction-scoped and
safe. A session-scoped `SET` (without `LOCAL`) must **not** be used — session
state is not guaranteed to reset between transactions across pooled clients.
Both Supabase pooler modes are relevant: 6543 is transaction pooling (used
today); 5432 would be session pooling. The design must behave under 6543, which
it does with `set_config(..., true)`.

**Concern to verify.** `session.py` uses `NullPool`, and the bridge session is a
single connection reused across many transactions. Every transaction on both
paths must run the `after_begin` hook — including the bridge path — and the
GUCs must be re-set on every transaction (they are cleared at commit).

## 7. Decision D8 — FORCE RLS vs non-owner role

**Recommendation: Option B — move the app connection to a non-owner,
non-BYPASSRLS role.** (With a decisive census caveat for Option A.)

Census caveat: the connection role `postgres` has **`rolbypassrls = true`**.
`FORCE ROW LEVEL SECURITY` makes the *owner* subject to RLS, but a role with the
`BYPASSRLS` attribute bypasses RLS regardless. Therefore **Option A (FORCE) does
not enforce on this connection** unless `BYPASSRLS` is also removed from
`postgres` — which is Supabase-managed and would make every owner operation
(migrations, seeders, maintenance, and the app) subject to RLS. Option A is
therefore not effective as-is.

Option B detail:

- The app issues **`SET LOCAL ROLE authenticated`** at the start of each
  transaction (transaction-scoped, so it cannot leak across pooled clients —
  unlike a session-level `SET ROLE`). **SME decision (Q2): reuse
  `authenticated`; do NOT create a new `app_rls` role.** It is a standard
  Supabase role, `postgres` is already a member, and the grants are in place.
- Migrations, seeders, and maintenance scripts keep connecting as the owner and
  do **not** `SET ROLE`, so they run outside RLS (as today) (Q9).

Reversibility: Option B is reversible by removing the `SET LOCAL ROLE` (the app
returns to the owner path). It also leaves the owner connection fully capable
for operations. Option A, if combined with removing `BYPASSRLS`, is the riskier
one to restore because that attribute is Supabase-managed.

## 8. The canonical policy template

All tenant-owned tables follow one shape. `USING` gates reads/updates/deletes;
`WITH CHECK` gates inserts/updates. `TO authenticated` — the app role (Q2: reuse
`authenticated`; no new role).

**Template A — uuid tenant column** (44 tables):

```sql
-- Comment: "SUPER_ADMIN is the platform owner; this exemption is intentional
-- and documented." (Q5)
DROP POLICY IF EXISTS p_<t>_tenant_isolation ON public.<t>;
CREATE POLICY p_<t>_tenant_isolation ON public.<t>
  AS PERMISSIVE
  FOR ALL
  TO authenticated
  USING (
    current_setting('app.current_role') = 'SUPER_ADMIN'
    OR <tenant_col> = current_setting('app.current_tenant')::uuid
  )
  WITH CHECK (
    current_setting('app.current_role') = 'SUPER_ADMIN'
    OR <tenant_col> = current_setting('app.current_tenant')::uuid
  );
```

For **Operator-only** tables (Q6) the regulator branch below is omitted, so the
policy is tenant + `SUPER_ADMIN` only. For **Outcome-visible** and
**Mandatory-report** tables the regulator branch is added.

**Template B — text tenant column** (`audit_logs`, `caan_reports`,
`audit_dispatches`, `tenants`, `sms_dispatches`): the same shape comparing the
slug:

```sql
  USING (
    current_setting('app.current_role') = 'SUPER_ADMIN'
    OR <tenant_col> = current_setting('app.current_tenant_slug')
  )
```

Both GUC variables are set in every transaction (Q4/Q11); each policy reads the
one it needs. No casts, no drift.

**Regulator oversight (Q6).** `STATE_SMD` does **not** get an RLS exemption. On
Outcome-visible and Mandatory-report tables only, the policy adds a branch:

```sql
    OR (
      current_setting('app.current_role') = 'STATE_SMD'
      AND EXISTS (
        SELECT 1 FROM public.oversight_relationships o
        WHERE o.regulator_tenant_id =
                current_setting('app.current_tenant')::uuid
          AND o.operator_tenant_id = <tenant_col>
          AND o.effective_to IS NULL
      )
    )
```

Operator-only tables omit this branch. The class of every table is enumerated in
§12. Regulators read; the app owns writes.

The SME predicates are recorded verbatim in §11. In implementation the
missing-ok form `current_setting('app.x', true)` is recommended so an unset
value yields NULL rather than raising a `missing_ok` error.

**Reference / read-all tables** keep a `USING (true)` read policy; no tenant
isolation is required.

**Identity / registry / audit tables** — special shapes, enumerated in §12:
- `users.user_read_own` → `uid = current_setting('app.current_user')`, plus a
  tenant-admin read policy keyed on the GUC tenant.
- `audit_logs_admin_only` → `current_setting('app.current_role') = 'SUPER_ADMIN'`
  for reads; the app's insert path is a separate policy
  `audit_logs_insert_app` (Q10).
- `tenants.tenant_read_own` → `tenant_id = current_setting('app.current_tenant_slug')`.

## 10. Risks

| Risk | Likelihood | Impact |
|---|---|---|
| Session GUC not honoured by the connection pooler | Medium | High — `SET LOCAL`/`set_config(...,true)` are transaction-scoped and supported, but must be verified against the live 6543 transaction pooler and the bridge session |
| Non-owner role availability | Low | High — `authenticated` exists, `postgres` is a member, and grants are in place (Q2); the residual risk is the pooler refusing `SET LOCAL ROLE` (Q3 verification in 2C.2) |
| Policy rewrite breaks a live path | Medium | High — the app has `NullPool` + a long-lived bridge session and both must set the GUC every transaction |
| FORCE RLS chosen and silently ineffective | Medium | High — the `postgres` role's `BYPASSRLS` means FORCE does not gate the app; this must be explicit in D8 |
| The two pooler modes behave differently with `SET LOCAL` | Medium | Medium/High — `SET LOCAL` is per-transaction (safe under transaction pooling); session `SET` is not |
| `SET LOCAL ROLE` session leak | Low | High — must use `SET LOCAL ROLE` (transaction-scoped), never session `SET ROLE`; verify the pooler resets state |
| Text vs uuid tenant columns | Medium | Medium — 5 tables store a text tenant; the template must branch, or two GUCs are set |
| Missing grants on the app role | Low | Low — `authenticated` already holds full DML on `public` tables and the default privileges; reusing it (Q2) removes the grant pass |
| Regulator predicate too broad or too narrow | Medium | High — oversight relationships are the source (Q6); the §12 class map governs which tables carry the branch |
