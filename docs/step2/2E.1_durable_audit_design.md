## 1. Current State Analysis

### 1.1 Where `log_audit()` writes

`backend/app/services/audit_service.py:24-63` is the single writer. It performs
two **best-effort** writes (failures are swallowed and only `logger.warning`'d,
so an audit failure never blocks the business request):

1. **Postgres — `public.audit_logs`** (primary) via `pg.insert(AuditLog, pg_doc)`
   (`audit_service.py:57`).
2. **Firestore — `audit_logs` collection** (mirror) via
   `get_db().collection("audit_logs").add(...)` (`audit_service.py:61`).

The entry shape (`audit_service.py:40-51`):

| field | Postgres column | notes |
|---|---|---|
| `action` | `action` | e.g. `VSR_SUBMITTED` |
| `user` | *(not persisted in PG)* → `actor` | `pg_doc["actor"] = user` |
| `tenant_id` | `tenant_id` | slug (text) |
| `target_type` / `target_id` | `target_type` / `target_id` | |
| `ip` / `request_id` | `ip` / `request_id` | from `request_context()` |
| `metadata` | `metadata_json` | JSONB |
| `timestamp` | `created_at` | tz-aware UTC |

**Inconsistency worth fixing in Phase 2E:** the Firestore mirror stores `user`
verbatim; the Postgres row stores it as `actor`. The Firestore `user` key does
not map to any Postgres column and is silently dropped by `_split_doc`. The two
sinks therefore have slightly different field names for the same concept
(`user` vs `actor`).

`pg.insert` (`backend/app/db/pg.py:330-355`) inserts **without `RETURNING`** and
supplies an explicit `id` (uuid4) specifically so append-only tables whose RLS
allows INSERT but restricts SELECT remain writable (`pg.py:333-337`).

### 1.2 Schema of `public.audit_logs`

`backend/app/db/schema_init.py:199-216` (also mirrored in
`backend/app/db/db_models.py:2267-2289`):

```
audit_logs (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  action        TEXT NOT NULL,
  actor         TEXT,          -- email or uid (see below)
  target        TEXT,          -- unused by log_audit()
  target_type   TEXT,
  target_id     TEXT,
  detail        TEXT,          -- unused by log_audit()
  result        TEXT,          -- unused by log_audit()
  tenant_id     TEXT,          -- slug
  ip            TEXT,          -- client IP (PII)
  request_id    TEXT,
  metadata_json JSONB NOT NULL DEFAULT '{}'::jsonb,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
)
Indexes: ix_audit_logs_tenant (tenant_id), ix_audit_logs_created (created_at)
```

**Is it mutable?** At the RLS layer it is effectively **append-only for the
`authenticated` app role**, but **not tamper-evident at the database level**:

- `audit_logs_admin_only` — `FOR SELECT TO public USING (auth.jwt() ->> 'role' = 'SUPER_ADMIN')`
  (`supabase/migrations/20261014130000_rls_unversioned_capture.sql:19-23`).
- `audit_logs_insert_authenticated` — `FOR INSERT TO authenticated WITH CHECK
  (tenant_id IS NULL OR tenant_id = app.current_tenant_slug OR
  app.current_role = 'SUPER_ADMIN')` (`supabase/migrations/20261020120000_vsr_anonymity.sql:119-128`,
  added in 9978899 to stop silent drop of inserts).

There is **no `UPDATE`/`DELETE` policy**, so the application cannot mutate rows
through RLS. However:

- The **owner/`service_role`** connection bypasses RLS and can `UPDATE`/`DELETE`.
- Several maintenance paths **delete audit rows**:
  - `backend/_purge_prod_database.py:18` includes `audit_logs`.
  - `backend/scripts/reset_to_virgin.py:89,167` includes `audit_logs`.
  - `backend/app/services/admin_data_service.py:1460,1518` wipes the Firestore
    `audit_logs` collection during demo-data purge.
  - `backend/seed/seeder.py:349,363-397` purges Firestore `audit_logs`.

So today the trail is append-only *by convention and RLS*, not by hard DB
guarantee, and it is explicitly purged in demo/reset flows.

### 1.3 Other implicit audit trails

There is no single durable trail today; the following are scattered, mutable,
and often not linked:

- **Row timestamps** — `created_at` / `updated_at` on `reports`, `hazards`,
  `cans`, `caps`, `reporter_contacts`, `psoe_assessments`, etc. These record
  *when* but not *who/what*.
- **Hazard register / master register** — `build_master_register`
  (`backend/app/services/master_register.py`) is a *derived view*, not a history.
- **State machine history** — `state_machine.update_hazard_register`
  (`backend/app/services/state_machine.py`) persists transitions for a narrow
  slice of the hazard lifecycle only.
- **Escalation history** — `escalation_service.py` writes `CAN_ESCALATED` /
  `CAP_OVERDUE` into `audit_logs`, and CAP `ae_signature` blocks hold the AE
  decision payload (immutable JSONB on `caps`).
- **Dispatch audit** — `backend/app/repositories/audit_repo.py` and the
  `sms_dispatches` table track regulatory/tenant email dispatch statuses
  (exposed via `/api/v1/state-risk/audit-logs` and `/api/v1/tenants/audit-logs`),
  but these are **dispatch** trails, not the general audit trail.
- **CAAN read audit** — `backend/app/services/caan_audit.py` writes
  `CAAN_READ_*` / `CAAN_SHARE_*` / `CAAN_ESCALATED_READ` into `audit_logs`.

**Conclusion:** the durable trail should be the single authoritative sink; the
other trails remain as operational views but are not relied upon for tamper
evidence.

### 2.2 Proposed missing events

1. `USER_ROLE_CHANGED` — role/tenant/department changes on `users`/`memberships`.
2. `AUTHORIZATION_DENIED` — emit from the 403 paths (route guards +
   `rbac_middleware`) with `metadata = {resource, reason, role}`. Rate-bounded to
   avoid audit-log flooding.
3. `REPORT_READ` — raw narrative/reporter reads (mirrors
   `REPORTER_CONTACT_READ`), so every read of protected content is reconstructible.
4. `HAZARD_STATUS_CHANGED`, `HAZARD_UPDATED`, `HAZARD_ASSIGNED`.
5. `CAN_STATUS_CHANGED`, `CAP_UPDATED`, `CAP_STATUS_CHANGED`.
6. `LOGIN_FAILED` — distinguish from successful `LOGIN` (already logged).

Every event must carry: `action`, `actor` (uid or `NULL` for anonymous VSR),
`tenant_id`, `target_type`, `target_id`, `request_id`, `created_at`, and a
**PII-reviewed** `metadata` (see §4).

## 3. Storage & Immutability Architecture

### 3.1 Option A — Postgres `durable_audit_logs` (recommended)

Create a new, purpose-built table:

```
durable_audit_logs (
  seq            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  event_id       UUID NOT NULL DEFAULT gen_random_uuid(),
  tenant_id      TEXT,
  actor_uid      TEXT,             -- opaque uid; NULL for anonymous
  actor_email    TEXT,             -- REDACTED by policy (see §4)
  action         TEXT NOT NULL,
  target_type    TEXT,
  target_id      TEXT,
  request_id     TEXT,
  ip_hash        TEXT,             -- sha256(ip + salt), never raw IP
  metadata_json  JSONB NOT NULL DEFAULT '{}'::jsonb,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  prev_hash      TEXT NOT NULL,
  current_hash   TEXT NOT NULL,
  UNIQUE (tenant_id, seq)          -- if per-tenant chains; else global seq
)
```

**Immutability — layered, not just RLS:**

1. **RLS:** `FOR INSERT TO authenticated` only; **no** `SELECT`/`UPDATE`/`DELETE`
   policy for `authenticated`. Reads go through a definer function / a dedicated
   read role (see §6).
2. **Revoke DML from `service_role` / owner:** add a `BEFORE UPDATE OR DELETE`
   trigger that raises `'durable_audit_logs is append-only'`; optionally revoke
   `UPDATE`/`DELETE` grants entirely and require `TRUNCATE` to be owner-gated.
3. **Append-only write path:** all inserts go through a
   `SECURITY DEFINER` function `append_durable_audit(...)` that (a) computes the
   hash chain server-side and (b) is the only grantee of `INSERT`. Direct table
   INSERT is revoked from `authenticated`.

**Hash chain (tamper evidence):**

```
current_hash = sha256( prev_hash
                     || tenant_id
                     || action
                     || target_type || target_id
                     || request_id
                     || ip_hash
                     || canonical_json(metadata_json)
                     || created_at )
```

- `prev_hash` of row N = `current_hash` of row N-1 (per-tenant chain anchored at
  a stored genesis hash; a **global** chain is simpler but serializes all
  writers — recommend per-tenant chains + one global anchor for SUPER_ADMIN).
- A verification endpoint recomputes the chain and flags the first break
  (`GET /api/v1/audit/verify`, §6).
- Optionally HMAC the hash with a server-held key so a DB-only attacker cannot
  silently re-chain. The key lives in the environment/secret manager, never in
  the DB.

### 3.2 Option B — Firestore / WORM only

Firestore is already a mirror, but relying on it as the durable sink has
problems:

- **No native hash chain** — tamper evidence would have to be computed in the
  app layer and is not enforceable at write time.
- **Query complexity** — time-range + tenant + action filtering across documents
  is awkward and expensive relative to a single indexed Postgres table.
- **Cost** — Firestore charges per document read/write; a durable trail that
  grows unbounded is a poor cost fit.
- **No single transaction boundary** with the business write (Postgres can write
  the audit row in the same transaction as the mutation).

**Firestore value is as an offline/backup mirror, not the system of record.**

### 3.3 Recommendation

**Postgres `durable_audit_logs` with a per-tenant hash chain + trigger-guarded
append-only + a SECURITY DEFINER append function.** Keep Firestore as a
best-effort export mirror only (optional, for DR/offline evidence), never as the
authoritative chain.

Rationale: it gives hard immutability (trigger + revoked DML), cryptographic
tamper evidence (hash chain/HMAC), transactional consistency with the business
write, and cheap indexed queries — all with the privacy controls of §4.

## 4. PII and Privacy

The durable trail must **never** re-link an anonymous VSR to its reporter. This
is a hard constraint from 2D.2 (VSR anonymity) and is already partially honored:

- `VSR_SUBMITTED` and `REPORTER_CONTACT_WRITTEN` write `user=None`
  (`occurrence_reports.py:141,271-273`; `confidential_reporting_service.py:249-260`).
- `REPORTER_CONTACT_WRITTEN` metadata contains **booleans** (`has_name`,
  `has_email`, `has_phone`), never the contact values.

Proposed rules for the durable trail:

1. **`actor`**: store `actor_uid` (opaque Firebase uid) by default. Store
   `actor_email` only for events where the actor is not a VSR reporter and the
   SME has approved email retention; otherwise `NULL`.
2. **VSR anonymity invariant**: for any event keyed to a VSR (`VSR_SUBMITTED`,
   `REPORTER_CONTACT_*`), force `actor_uid = NULL` and forbid metadata from
   carrying `reporter_*` values. Add an automated check in the append function /
   a test that asserts the metadata keys are on an allow-list.
3. **IP address**: do **not** store raw IP in the durable table. Store
   `ip_hash = sha256(ip || static_salt)` so correlation across events is possible
   without retaining the raw address. (Open question Q-PII-1.)
4. **Metadata allow-list**: define per-action allowed metadata keys and reject
   unknown keys at the append boundary; this prevents accidental PII leakage via
   future call sites.
5. **Redaction on read**: the read API (and any export) returns `actor_email` and
   `ip` redacted (`actor_uid`/`ip_hash` only) unless the caller is `SUPER_ADMIN`
   with an explicit `include_identifiers=true` and the event is non-VSR.

**Current PII in the trail to correct:** today `actor` is frequently a raw email
(e.g. `log_audit(user=user.get("email"))` throughout). The migration in §5
should classify existing rows and redact `actor` → `actor_uid` where an email is
present and the event is not an approved non-VSR administrative event.

## 5. Migration Strategy (Path C)

Cut over from `audit_logs` → `durable_audit_logs` with zero event loss.

1. **Create the new table + append function + trigger** (idempotent migration).
   Do **not** yet switch writers.
2. **Dual-write window**: `log_audit()` writes to both `audit_logs` (legacy) and
   `durable_audit_logs` (new) for a defined soak period. A reconciliation job
   asserts counts match per `(tenant_id, action, created_at)` bucket.
3. **Backfill**: copy all historical `audit_logs` rows into
   `durable_audit_logs` ordered by `created_at, id`, computing the hash chain
   from the oldest row. Redact PII during the copy (§4). Record a genesis hash
   and a `migration_cutover` marker row.
4. **Verify**: run `GET /api/v1/audit/verify` and a row-count + checksum
   comparison. A backfill report (rows copied, rows redacted, first/last hash)
   is persisted for the record.
5. **Freeze legacy**: revoke `INSERT` on `audit_logs`; leave it read-only
   (SUPER_ADMIN) as the pre-cutover archive. Stop the dual-write.
6. **Post-cutover**: `log_audit()` targets only `durable_audit_logs`. Firestore
   mirror continues (or is retired per SME).

**No-loss guarantee:** every write path funnels through `log_audit()`, so a
single dual-write in that one function covers all ~64 call sites. Because the
append function computes the hash atomically in the same transaction as the
business mutation (where possible), there is no window where a business write
succeeds without an audit row.

## 6. Read / Query API

### 6.1 Who reads it

- **`SUPER_ADMIN`** — full read (all tenants, all actions), for incident
  response and compliance evidence. May see `actor_uid`/`actor_email` (non-VSR)
  and `ip_hash`; raw `ip` never stored.
- **`STATE_SMD`** — read-only *compliance* view: cross-tenant aggregate counts
  and a restricted action set (`CAAN_READ_*`, `CAAN_SHARE_*`,
  `CAAN_ESCALATED_READ`, `MOR_REGULATORY_SUBMITTED`, `STATE_SPT_*`), **no** raw
  VSR/reporter events, **no** PII. (Open question Q-READ-1: is STATE_SMD a
  reader at all, or SUPER_ADMIN only?)
- **`TENANT_ADMIN`** — own-tenant events only, excluding anonymous VSR identity
  events (consistent with 2D.2 custody).

### 6.2 Proposed endpoints (design only)

```
GET /api/v1/audit/
  ?tenant_id=&action=&target_type=&target_id=&from=&to=&limit=
  RLS: SUPER_ADMIN (all) | STATE_SMD (restricted set) | TENANT_ADMIN (own tenant)
  Response: list of {seq, event_id, action, actor_uid, actor_email(redacted),
                     target_type, target_id, request_id, created_at, current_hash}

GET /api/v1/audit/verify?tenant_id=
  Recomputes the hash chain and returns {valid, first_break_seq, count, last_hash}
  RLS: SUPER_ADMIN only
```

**RLS sketch (durable table):**
- `durable_audit_select_super` — `SELECT` to a `super_audit` role / `SUPER_ADMIN`.
- `durable_audit_select_tenant` — `SELECT` to `authenticated` where
  `tenant_id = app.current_tenant_slug AND action NOT LIKE 'VSR_%' AND
  action NOT LIKE 'REPORTER_CONTACT_%'`.
- No `UPDATE`/`DELETE` policy for any role.

## 7. Open Questions for SME

- **Q-PII-1** — Is `ip_hash` (salted) acceptable, or must IP be dropped entirely
  from the durable trail?
- **Q-READ-1** — Is `STATE_SMD` a compliance reader of the durable audit, or is
  read access `SUPER_ADMIN`-only?
- **Q-RET-1** — Retention/archival policy: how long is the trail kept online,
  and is there a cold-archive (e.g. object storage) after N years?
- **Q-CHAIN-1** — Per-tenant chains vs one global chain (global is simpler to
  verify; per-tenant avoids cross-tenant write serialization).
- **Q-SIGN-1** — Use HMAC with a server-held key (stronger) or a plain SHA-256
  chain (simpler, keyless)?
- **Q-READ-2** — Should raw *read* events (`REPORT_READ`) be included, or writes
  only (reads are higher volume)?
- **Q-PURGE-1** — Demo/reset flows currently delete `audit_logs`. Must the
  durable table be exempt from demo purge, or is a "purge is itself an audited
  event" model acceptable?
- **Q-MIRROR-1** — Keep the Firestore mirror as DR/offline evidence, or retire it
  once the durable Postgres table is authoritative?
