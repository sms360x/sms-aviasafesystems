# 2A.5 — Revert the auth boundary; retain memberships as the Super-Admin reporting substrate

Status: complete. Branch: `step2-governance`. Date: 2026-10-12.

## 1. SME ruling

SME ruling (2026-10-12):

- **One user = one tenant = one role** (ICAO accountability).
- The **auth boundary reads from the `users` row**.
- The `memberships` table is retained as a **Super-Admin-only reporting
  substrate**. It is not read by any operational code path.
- It is kept **in sync when users are created or roles change**.

This is a partial revert of 2A.4. It keeps the schema additions (the
`memberships` and `oversight_relationships` tables) and the tenant unification
(2A.3b / 2A.3b-code). 2A.6 was not started.

## 2. Revert of the auth boundary

`backend/app/middleware/auth.py`:

- `resolve_user_context(email)` now reads `role` and `tenant_id` directly from
  the **`users` row** (the `UserProfile` lookup) and resolves the stored
  `tenant_id` uuid to its tenant slug. The token's role/tenant are not used.
- Removed the membership query (`_active_membership`) and the
  `_membership_tenant_slug` helper (replaced by `_tenant_slug`, which resolves
  the **users** row's `tenant_id` to a slug).
- Removed the `tenant_id` parameter from `resolve_user_context` (it only ever
  supported explicit-tenant resolution, which is no longer used at the
  boundary).
- A missing `users` row yields `{"role": None, "tenant_id": None}` and a WARN
  log; protected endpoints then deny.

Callers updated to the new single-argument signature:

- `get_current_user` (`app/middleware/auth.py`).
- `POST /api/v1/auth/verify` (`app/routes/auth.py`).

Not reverted (per §1.3): the `memberships` and `oversight_relationships`
tables, the tenant unification (2A.3b), the `tenants.kind` column, and the ORM
single-table inheritance (2A.3b-code).

## 3. Memberships retained as a reporting substrate

### Schema

`public.memberships` columns confirmed: `id, user_id, tenant_id, role,
effective_from, effective_to, is_active, created_at, updated_at`.

The one-active-row-per-user unique index was **missing** (the earlier 2A.5
membership-coverage pass was never committed). Added:

- Migration `supabase/migrations/20261012120000_memberships_one_active_per_user.sql`:
  `CREATE UNIQUE INDEX IF NOT EXISTS memberships_one_active_per_user ON
  public.memberships (user_id) WHERE is_active = true;`
- Mirrored in the ORM (`app/db/db_models.py`, `Membership.__table_args__`).

The pre-existing `memberships_active_unique` index
(`user_id, tenant_id, role` where active and open-ended) is retained.

### Sync mechanism

- `users.upsert_user_doc` now calls the sync on **every** user write (not only
  on creation), so both creation and role/tenant changes keep the substrate
  current. Previously the membership write was gated on genuine creation.
- New `users.update_membership_role(uid, role, tenant_id=None)` — the named
  sync entry point — delegates to the existing `users.ensure_membership`, which
  upserts exactly one active row per user keyed by `user_id` (idempotent). The
  row is updated in place on a role change.

All user role-change paths funnel through `upsert_user_doc`
(`admin_update_user` → `upsert_user_doc`; `POST /auth/verify`-adjacent `/me`
update; admin claims updates), so no separate call site was required.

## 6. G9 / G12 defects are moot

The earlier coverage pass surfaced two defects in the **membership-based**
resolver:

- **G9** — a future-dated membership (`effective_from` in the future) was
  selected as the current context.
- **G12** — the explicit request-tenant parameter was accepted but ignored.

Both existed only in the membership resolver, which is now reverted. Under the
corrected model the auth boundary reads the single (user, tenant, role) tuple
from the users row; there is no membership selection and no explicit-request
tenant parameter, so neither defect applies. The tests that documented them
have been removed with the revert.
