# 2A.4 — auth boundary reads from memberships

PHASE: 2A

## 1. Change summary

The auth boundary now reads the caller's role and tenant **only** from the
`memberships` table. The token's `role`/`tenant_id` claims are ignored. There is
**no feature flag and no fallback**; a user with no active membership resolves to
`role=None` / `tenant_id=None` and is denied by every protected endpoint.

`app/middleware/auth.py`:

- New `_active_membership(user_uuid)` — active membership (`is_active`,
  `effective_to IS NULL`); newest `effective_from` wins, ties broken by `id`.
- New `_membership_tenant_slug(uuid)` — `memberships.tenant_id` (uuid) → tenant
  slug via the `tenants` table, falling back to the canonical `uuid5` slug.
- `resolve_user_context(email, role, tenant_id)` rewritten: look up the user by
  email → resolve the actor UUID (`app.services.actor.resolve_actor_uuid`) →
  read the active membership → return `{"role", "tenant_id"}`. On a missing user
  or membership it logs a WARN and returns `{"role": None, "tenant_id": None}`.
  The token `role`/`tenant_id` arguments are accepted but unused.
- The previous claim-mapping helpers (`_ROLE_CLAIM_ALIASES`,
  `_lookup_tenant_by_email`, `get_tenant_slug_from_email`) are retained but no
  longer on the resolution path.

`get_current_user` (2.2) is **unchanged** in behaviour: it still verifies the
token, calls `resolve_user_context`, applies the suspended-tenant gate, and
returns the user dict. `department` still comes from the token, **not** the
`users` row — recorded as a finding (out of 2A.4 scope).

## 2. User-creation paths write a membership

`app/services/users.py`:

- `upsert_user_doc(...)` now probes `_existed = pg.fetch_by(UserProfile, "uid",
  uid) is not None` before the upsert. When the row did **not** previously exist
  (genuine creation) it calls `ensure_membership(uid, tenant_id, role or "USER")`.
  Claims refreshes / updates of existing users do not re-write a membership.
- New `ensure_membership(uid, tenant_id, role)` — best-effort (never raises):
  resolves the users UUID PK via `pg.fetch_by(UserProfile, "uid", uid)`, then
  `pg.upsert(Membership, "user_id", user_id, doc)` with
  `effective_from=now`, `effective_to=None`, `is_active=True`; `tenant_id` is
  normalised with `_resolve_tenant_id` (slug or uuid → canonical uuid5; None
  means platform/cross-tenant).

This centralises coverage: every creation path that funnels through
`upsert_user_doc` (tenant registration, the seeders, `seed.users.create_user`)
writes a membership without per-caller changes.

## 3. Downstream readers

Readers of `resolve_user_context` are unchanged: `get_current_user`
(`auth.py`) and `POST /api/v1/auth/verify` (`routes/auth.py`). Both consume the
`{"role", "tenant_id"}` dict, so no call-site changes were required.

Findings (not fixed in 2A.4):

- With `role=None`, readers that assume a non-null role would misbehave. In the
  current data set every live user has a membership (20/20), so no live request
  path hits `role=None`; the boundary still returns it by design for the
  no-membership case and the endpoint gates deny.
- `department` remains token-derived; it is not read from `users`/`memberships`.
