## 1. Current state (census)

- **No reporter-contact store exists.** 60 public tables; none matches
  `%reporter%`, `%contact%`, or `%custodian%`. Reporter contact lives on the
  `reports` row itself.
- **Reporter metadata is on `reports`**: `reporter_name`, `reporter_role`,
  `reporter_email`, `reporter_phone`, `reporter_organisation` (all `text NULL`)
  plus `reporting_date` (`timestamptz NULL`) — `db_models.py:259-264`.
- **The confidential service is unwired.** `ConfidentialReportingService`
  (`confidential_reporting_service.py`) is imported only by
  `backend/tests/test_confidential_reporting.py`. No route/service calls
  `mark_confidential`, `deidentify`, `get_for_downstream`, or
  `can_view_reporter_identity`.
- **Nothing is marked confidential.** `reports.is_confidential` defaults `false`
  (`db_models.py:285-287`); 0 live rows are confidential; 0 rows have a
  `confidential_custodian_id`.
- **No de-identification on read.** `_to_report_response` returns the reporter
  fields verbatim to any caller that passes the route gate; `_to_list_item`
  omits them by projection only.
- **The role conflict that stopped 1C.1b-i is resolved.** 2C.7 replaced
  `_RAW_VSR_ROLES` with the department-based `can_view_raw_vsr(user)`
  (TENANT_ADMIN, or OFFICER with `department == 'safety'`, or the legacy
  `SAFETY_OFFICER` literal).
- **No VSR rows carry reporter metadata** (see §7) → **no backfill decision is
  forced** at this item.

**Stop conditions (§6 of the instruction): none triggered.** The `reports`
structure matches the assumption; the service exposes exactly the four functions
listed; there is no existing (partial) contact store; no VSR row carries reporter
metadata needing a backfill.

## 4. The submission path

`create_report` (`report_service.py:343-415`) iterates `Report.__table__.columns`
and builds `values` from the request payload, then inserts via
`_create_report_async` (`:119-124`). It is shared by all three POST endpoints in
`routes/occurrence_reports.py`:

- `submit_report` (`POST /`, `:117-146`) — `ReportCreate` (type defaults
  `voluntary`). Legacy path.
- `submit_mor` (`POST /mor`, `:151-221`) — `MorCreate`; reporter fields are
  **mandatory** and validated (`models/report.py:162-166`, `EmailStr`); sets
  `report_type="mandatory"`, `is_anonymous=False`.
- `submit_vsr` (`POST /vsr`, `:226-273`) — `ReportCreate`; reporter fields
  optional; if `reporter_name` is absent it is set to the literal
  `"Anonymous"` and `is_anonymous=True` (`:244-246`); sets
  `report_type="voluntary"`.

Findings:

- **Reporter fields are written verbatim from the request payload** into the
  `reports` row (no split, no derivation, no second store).
- **`is_confidential` is never set** by any submission path (payloads do not
  carry it), so rows are created non-confidential (column default `false`).
- **`mark_confidential` is never called**; no custodian is assigned at
  submission.
- `submit_vsr`/`submit_report` also call `_auto_create_hazard_from_report`
  (`:501+`), which copies `narrative` into the hazard title/description. The
  hazard carries **no reporter-identity columns** (so the metadata does not leak
  there), but the narrative content does (self-identified names remain — 1D §Q3).

## 5. The read path

The single read endpoint pair is `get_reports` (`GET /`, list) and `get_report`
(`GET /{report_id}`, detail) in `routes/occurrence_reports.py`; both build a
`ReportService` and delegate to `get_reports` / `get_report_by_id`
(`report_service.py:417-440`).

- **List** → `_to_list_item` (`:470-494`): returns id/tenant/type/status/location/
  dates/risk/aircraft/flight — **no reporter fields** (projection only).
- **Detail** → `_to_report_response` (`:436-467`): returns the full shape
  **including `reporter_name`, `reporter_role`, `reporter_email`,
  `reporter_phone`, `reporter_organisation`, `reporting_date`** (`:459-460`).

Role effect today:

- **Tenant scoping** is decided in the *service* via
  `settings.CROSS_TENANT_ROLES` (`report_service.py:419,433`); a cross-tenant VSR
  returns `None` → 404 (`:154-155`).
- **Raw access** is decided in the *route* by `can_view_raw_vsr(user)`
  (2C.7): a same-tenant non-raw caller gets 403 **before** composition;
  cross-tenant roles bypass the check (list keeps its existing behaviour).
- **De-identification does not happen.** `_to_report_response` returns reporter
  identity to every caller that reaches it (TENANT_ADMIN, Safety-Dept OFFICER,
  cross-tenant roles). This confirms `1D_reporter_redaction_check.md` §Q2:
  `deidentify` exists but is unwired.

## 6. The custodian rule

Under the corrected model (2B.1 §12 Q6 as implemented by 2C.7), **custodian ==
`can_view_raw_vsr`**:

    TENANT_ADMIN
    OR (OFFICER AND department == 'safety')
    OR SAFETY_OFFICER   (defensive)

Existing code paths:

| Path | Rule | Members | Status |
|---|---|---|---|
| `occurrence_reports.can_view_raw_vsr` (2C.7) | role + department | TENANT_ADMIN, OFFICER+safety, SAFETY_OFFICER | **in force** |
| `confidential_reporting_service.CUSTODIAN_ROLES` | role set (+ per-user custodian match) | TENANT_ADMIN, AIRLINE_ADMIN, SUPER_ADMIN | unwired; **stale** |
| `master_register.REPORT_VIEWER_ROLES` | role set | TENANT_ADMIN, SAFETY_OFFICER, OFFICER, SUPER_ADMIN | register-row visibility (a *different* rule — 2B.4b §2) |

`CUSTODIAN_ROLES` is **inconsistent with 2C.7**: it omits the Safety-Department
OFFICER and carries the retired `AIRLINE_ADMIN` (2B.3 → `TENANT_ADMIN`) plus
`SUPER_ADMIN`. `can_view_reporter_identity` also applies a *per-user* custodian
match (`confidential_custodian_id`), which is a different concept from the
department rule. This is the same three-way conflict 1C.1b-i recorded; only the
raw-access leg was reconciled (2C.7). The custodian leg must be reconciled in
2D.3 (§11).

`REPORT_VIEWER_ROLES` is **out of scope**: it governs register-row visibility,
not raw VSR / reporter identity (2B.4b §2; `master_register.py:37-38` warns
`is_confidential` is dormant and must not gate).

## 8. Proposed `reporter_contacts` table

Recommended shape (one row per report that has reporter contact):

    reporter_contacts
        id                        uuid PK      default gen_random_uuid()
        report_id                 uuid NOT NULL  UNIQUE  FK reports(id) ON DELETE CASCADE
        tenant_id                 uuid NOT NULL          FK tenants(id)
        reporter_name             text NULL
        reporter_email            text NULL
        reporter_phone            text NULL
        reporter_role             text NULL
        reporter_organisation     text NULL
        created_at                timestamptz NOT NULL default now()
        updated_at                timestamptz NOT NULL default now()

Changes vs the instruction's sketch: add `tenant_id` (so RLS can scope the row
without a join to `reports`), and `ON DELETE CASCADE` (contact is subordinate to
the report). `report_id UNIQUE` gives the 1:1.

**Why separate from `reports`:**

1. **RLS is row-level, not column-level.** `reports` RLS policies
   (Phase 2C) are `USING (<tenant predicate>)`; they cannot hide *columns*. A
   custodian-only rule over reporter identity is impossible while the PII shares
   a row with content a broader audience may legitimately read. Splitting the
   PII into its own table lets RLS deny the **whole row** to non-custodians.
2. **De-identification becomes structural.** Today `deidentify()` nulls fields
   at runtime. After the split, a non-custodian read simply **does not join**
   `reporter_contacts`; there is no PII to null and no risk of a missed field.
3. **Blast-radius reduction.** `reports` is read by registers, dashboards, and
   (in some paths) cross-tenant roles. Keeping identity off that row means those
   paths structurally cannot leak it (defence in depth for the 1D finding).
4. **Auditability.** Custodian reads can be audited on the contact store alone.

**Why this shape:** 1:1 (`report_id UNIQUE`) matches the single reporter/one
report model; `ON DELETE CASCADE` keeps it consistent with report lifecycle;
`tenant_id` denormalises the scope for RLS; the five PII columns mirror
`_IDENTITY_FIELDS` exactly, so the service needs no renaming.

**RLS:** see §12 — custodian-only read; insert/update/delete only on the app
write path (owner) or by the custodian.

## 9. Proposed `reports`-row changes (post split)

After the store exists, the reporter columns on `reports` are the source of a
migration and the question is whether new writes still populate them.

**Recommendation: option (c) — keep `reporter_*` for backward-compat only; all
new writes go to `reporter_contacts`.**

- (a) *Drop the columns* is the cleanest long-term, but `reports.reporter_*` is
  referenced by `_to_report_response`, `_report_to_dict`, the ORM model, the
  `deidentify` path, and RLS/seed/migration code; dropping is a schema change
  with a wide test surface. Defer the drop to a later cleanup.
- (b) *Denormalized cache* reintroduces the leak (a copy of the PII stays on the
  broadly-read `reports` row and would have to be kept in sync) and defeats the
  isolation rationale in §8. Rejected.
- **(c) Recommended**: `reporter_contacts` is the source of truth for new
  submissions; the `reports.reporter_*` columns are **deprecated** (NULL for new
  VSRs; left as-is for legacy rows), and a follow-up item drops them once no
  reader depends on them.

Consequences:
- **`is_confidential`** is set at submission for VSRs (they are confidential by
  class). **By whom:** in `create_report`/`submit_vsr` (application), not by a DB
  trigger — a trigger cannot see the department rule and would duplicate policy.
  (Alternatively a table `DEFAULT`/`CHECK` keyed on `report_type='voluntary'`;
  the SME should confirm — §16 Q3.)
- **`confidential_custodian_id`** = the resolved Safety-Department custodian for
  the tenant (the OFFICER whose `department='safety'`, or the TENANT_ADMIN if
  none). This is a 2D.3 decision (§10/§16 Q4).
- **De-identification on read** is applied to non-custodians (§10), which after
  the split means "do not return the contact block".

## 10. Integration points for the service

Proposed call sites (2D.3), keeping the service as the single policy home:

| Function | Call site | Notes |
|---|---|---|
| `mark_confidential` | `create_report` for `report_type == 'voluntary'` (or `submit_vsr`), passing the resolved custodian user | sets `is_confidential=True` + `confidential_custodian_id` at submission; for MOR, not called (MOR is not the confidential class) |
| write contact row | `create_report` (VSR: from the payload `reporter_*`; MOR: see §14) | writes `reporter_contacts` instead of the `reports` columns |
| `can_view_reporter_identity` | `get_report` (detail) gate, for the contact block | **reconciled to defer to `can_view_raw_vsr`** (§11) |
| `deidentify` / `get_for_downstream` | `get_report` (detail) for a confidential row when the caller is not the custodian, and the (future) AE/downstream aggregate path | returns the identity-free projection |

The list path (`_to_list_item`) needs no change: it never returns reporter
fields.

**Recommended minimal wiring for 2D.3:** submission writes the contact row and
sets `is_confidential`; the detail read returns the contact block only to
custodians (and audits the de-identified read for others). Avoid wiring
`get_for_downstream`'s extra `reports` re-read on the hot path — prefer calling
`deidentify` on the already-loaded dict.

## 11. Interaction with `can_view_raw_vsr`

The 2C.7 rule is `role + department only`. The new store does **not** change
it: reporter identity visibility == raw-VSR visibility (the same custodian
audience). So:

- **`can_view_reporter_identity` should defer to `can_view_raw_vsr`** —
  recommend the service import and call it (or accept the boolean from the
  caller) rather than keep `CUSTODIAN_ROLES`. This retires the stale
  `AIRLINE_ADMIN`/`SUPER_ADMIN` set and removes the duplicated rule.
- The **per-user `confidential_custodian_id` match** is a *second, narrower*
  concept (a named custodian). Recommendation: keep it as an **additional**
  condition inside confidential rows (custodian = the designated user, who must
  also pass `can_view_raw_vsr`), not as a replacement for the department rule.
  SME to confirm whether the named-custodian concept stays (§16 Q4).
- `SUPER_ADMIN`: today `can_view_reporter_identity` grants `SUPER_ADMIN` raw
  identity, but 2C.7's `can_view_raw_vsr` does **not** (SUPER_ADMIN is
  cross-tenant and excluded from raw VSR by 1A.7). For identity, recommend
  **not** granting SUPER_ADMIN (platform operator, not operator staff); if a
  break-glass read is needed it must be an audited override, not a silent allow.
  (§16 Q5.)

**Do not duplicate** the department rule in the service; defer to
`can_view_raw_vsr`.

## 12. RLS policy for the new table

Consistent with Phase 2C (app identity via ContextVar → `SET LOCAL ROLE
authenticated` + `app.current_*` GUCs):

    ALTER TABLE public.reporter_contacts ENABLE ROW LEVEL SECURITY;
    ALTER TABLE public.reporter_contacts FORCE ROW LEVEL SECURITY;

    -- Custodian read: the tenant's Safety Manager or Safety-Department officer.
    CREATE POLICY reporter_contacts_custodian_read ON public.reporter_contacts
      FOR SELECT
      USING (
        tenant_id = nullif(current_setting('app.current_tenant', true), '')::uuid
        AND (
          current_setting('app.current_role', true) = 'TENANT_ADMIN'
          OR (current_setting('app.current_role', true) = 'OFFICER'
              AND <department predicate>)
        )
      );

    -- Writes only on the owner path (migrations/seeders); the app writes via the
    -- authenticated role at submission, so an INSERT policy is also required.

**The department predicate is the crux.** The Phase 2C identity listener carries
`app.current_tenant`, `app.current_role`, `app.current_user`,
`app.current_is_developer` — **not** `department`. Two options:

- **(A) Add `app.current_department`** to the 2C identity listener and the
  ContextVar (`db/rls.py`), then the policy compares it to `'safety'`. Strongest
  (fully DB-enforced), but it extends Phase 2C identity code — a cross-item
  change.
- **(B) RLS enforces tenant scope + the named custodian; the department branch
  stays application-level** (`can_view_raw_vsr`). Policy:
  `tenant match AND (role='TENANT_ADMIN' OR app.current_user = confidential_custodian_id)`.
  Minimal, but the department nuance is not DB-enforced (defence-in-depth is
  partial).

**Recommendation: (B) for 2D.3**, with (A) recorded as the hardening item — it
avoids touching the 2C identity listener now, and the app-level rule is already
the single source of truth (2C.7). RLS remains the backstop for tenant scope and
the named custodian.

**Others → 0 rows:** by default, `USING` with no matching branch returns no rows,
so every non-custodian (STAFF, DEPT_ADMIN, cross-tenant) sees nothing.

**SUPER_ADMIN:** recommend **no** direct read (as §11). Tradeoff: a platform
operator loses break-glass visibility of reporter identity; the alternative (a
`SUPER_ADMIN` branch) re-introduces the very exposure the store exists to
prevent. If required, make it an audited, separately-granted override.

## 13. Migration strategy

Because **0 rows carry reporter metadata** (§7), there is **no backfill
required** at 2D.1. The migration plan for 2D.2:

1. `CREATE TABLE reporter_contacts` (+ indexes: `UNIQUE(report_id)`,
   `INDEX(tenant_id)`), enable + force RLS, add policies (§12).
2. (If the SME wants legacy preservation — **not required** given 0 rows:)
   a one-shot `INSERT INTO reporter_contacts SELECT ... FROM reports WHERE
   reporter_email IS NOT NULL OR reporter_name IS NOT NULL` before the columns
   are deprecated. With the current data this inserts 0 rows.
3. Do **not** drop `reports.reporter_*` in 2D (option (c §9)); schedule the drop
   for a later cleanup once `_to_report_response`/`_report_to_dict` stop reading
   them.

No column change to `reports` in 2D.2 beyond leaving the deprecated columns in
place. This is an additive migration (matches 2A.2/2B.2 convention).

## 14. MOR vs VSR handling

- **VSR (voluntary)** — the confidential class. Reporter identity is
  **custodian-only**; the contact block goes to `reporter_contacts`; `reports`
  rows for new VSRs leave `reporter_*` NULL; `is_confidential=True`.
- **MOR (mandatory)** — **statutory**, named (CAAN/ICAO Annex 13): the reporter
  is identified and the regulator has a right to the identity through the
  statutory channel (`MorCreate` requires name/role/org/email —
  `models/report.py:162-166`).

**Recommendation for MOR:** keep MOR reporter identity **on the `reports` row
(no split)**, or write it to `reporter_contacts` with a **regulator-visible RLS
branch** if one store is preferred for uniformity. Rationale:

- MOR must not be confidential: `is_confidential` stays `false`; the MOR path
  does **not** call `mark_confidential`.
- If MOR uses `reporter_contacts`, the policy needs a regulator read branch
  (STATE_SMD via the oversight/statutory path) — otherwise MOR identity becomes
  inaccessible to the regulator and breaks the statutory flow.
- Simplest and lowest-risk: **MOR stays on `reports.reporter_*`** (a MOR row is
  already regulator-visible; the columns are not the leak the store targets, and
  MORs are named by design). The store targets **VSR** identity. SME to confirm
  (§16 Q6).

Flag: if MOR is left on `reports` and VSR moved to `reporter_contacts`, the
`reports.reporter_*` columns cannot be dropped until MOR is also migrated (or
kept indefinitely as the MOR home). This affects §9's drop timing.

## 15. Risks

1. **Split-store desync** — a caller that writes `reports` but not
   `reporter_contacts` (or vice versa) yields a report with no/old identity.
   Mitigation: single write site in `create_report`; a covering test.
2. **Partial de-identification** — any path that still selects
   `reports.reporter_*` (legacy rows or MOR) can leak. Mitigation: option (c)
   keeps legacy values; the detail path must choose source by `report_type`.
3. **RLS gap on the department branch** (§12 option B) — the department nuance is
   app-level only. Mitigation: option (A) later; app rule is authoritative today.
4. **SUPER_ADMIN / break-glass** — removing SUPER_ADMIN identity access (§11) may
   surprise operators; needs an explicit, audited override if required.
5. **Narrative leakage** — reporter identity in the narrative (self-identified
   name) is not addressed by the store; the hazard auto-create copies the
   narrative (§4). Out of scope here but recorded (1D §Q3).
6. **`is_confidential` default semantics** — the create path does not set
   `is_confidential`; 2D.3 must set it explicitly for VSRs (and confirm the
   column binds correctly for the untouched paths).
7. **Custodian availability** — a tenant with no Safety-Department OFFICER needs
   a custodian; falling back to TENANT_ADMIN must be explicit.
