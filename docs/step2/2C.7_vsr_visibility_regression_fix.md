## 1. The three-way conflict

Three documents disagreed on who may read the **raw** VSR (narrative + reporter
identity), and the code matched none of them cleanly:

- **`docs/step1/1C.1_vsr_visibility.md`** (2026-10-10) — literal-role rule:
  `TENANT_ADMIN`/`AIRLINE_ADMIN` and the legacy `SAFETY_OFFICER` literal allowed;
  `DEPT_ADMIN`, `OFFICER`, `USER`, `STAFF` denied. The doc is explicit (§3) that
  the check keys on the *literal* `settings.ROLE_SAFETY_OFFICER`, **not** the
  dual-accept `SAFETY_OFFICER_ROLES` list, "intentional for 1C.1"; the
  OFFICER-as-rename unification was deferred to Step 2.
- **`docs/step2/2B.1_role_model_design.md` §12** (SME 2026-10-12, Q6) —
  department-based rule, expressed once:
  ```
  report_access(user, tenant):
      role == TENANT_ADMIN
      OR (role == OFFICER AND user.department == tenant.safety_department_name)
  ```
  with the fallback: `safety_department_name IS NULL` → `{TENANT_ADMIN}` only.
  The legacy `SAFETY_OFFICER` literal is retired to `OFFICER` + department.
- **`docs/step2/2B.4b_role_model_cleanup.md`** — recorded that the collapse of
  `_RAW_VSR_ROLES`/`CUSTODIAN_ROLES` into the department rule was **deferred**
  (the call sites did not all carry the tenant context the rule needs), and that
  `tenants.safety_department_name` was read by no authorization path.

**Why `9a9335a` introduced the regression.** Commit `9a9335a` ("fix(auth):
align canonical regulator and officer permissions", 2026-10-15) rewrote the
constant from the literal-only set to:
```python
_RAW_VSR_ROLES = (set(settings.TENANT_ADMIN_ROLES)
                  | set(settings.SAFETY_OFFICER_ROLES)   # == {"OFFICER"}
                  | {"SAFETY_OFFICER"})
```
This granted **every** canonical `OFFICER` raw-VSR access *unconditionally* — it
contradicted the 1C.1 literal rule and did **not** implement the 2B.1 Q6
department gate either. Result: `test_officer_denied_raw_vsr` (T5) and
`test_list_denied_for_non_raw_vsr_roles[OFFICER]` (T8) failed (200 instead of
403). The 2C.5 full-suite run (15 Oct 07:07) predated `9a9335a` (15 Oct 16:29),
which is why the failures had not appeared earlier.

## 2. SME ruling (2026-10-17)

- `'safety'` is the **universal canonical department code** for the Safety
  Department (`config.py` `DEPARTMENT_CODES`: `("safety", "Safety")`; established
  by 2B.4a, migration `20261012150000_department_codes_all_tables.sql`).
- The raw-VSR rule compares `user.department == 'safety'` **directly**. No
  tenant field is consulted.
- `tenants.safety_department_name` becomes a **display label only**; it is not
  used for access control.
- The 10 test-residue `SAFETY_OFFICER` users are **deleted**, not migrated.
- The `SAFETY_OFFICER` literal is **retained** as a defensive fallback in the
  rule (harmless — no live user has that role).

This supersedes the earlier "Option C with a tenant comparison" draft: the
department input is the user's own canonical code, so no tenant read is needed.

## 3. Code change

### 3.1 `backend/app/routes/occurrence_reports.py`

Removed the module constant `_RAW_VSR_ROLES`. Added a single helper used by both
endpoints:

```python
def can_view_raw_vsr(user: Dict[str, Any]) -> bool:
    """Raw VSR access per SME ruling 2026-10-17.

    Allowed:
        - TENANT_ADMIN (the Safety Manager)
        - OFFICER whose department is 'safety' (the canonical code)
        - SAFETY_OFFICER literal (defensive fallback; no live users have it)
    """
    role = user.get("role")
    if role in settings.TENANT_ADMIN_ROLES:
        return True
    if role == settings.ROLE_SAFETY_OFFICER:
        return True
    if role == settings.ROLE_OFFICER:
        if user.get("department") == "safety":
            return True
    return False
```

- `get_reports` (list): `if user.role not in CROSS_TENANT_ROLES and not
  can_view_raw_vsr(user)` → 403.
- `get_report` (detail): `if report_type == "voluntary" and user.role not in
  CROSS_TENANT_ROLES and not can_view_raw_vsr(user)` → 403.

No tenant lookup is performed (no `pg`/`Tenant` import was added; the earlier
draft's `_resolve_tenant` helper was removed).

### 3.2 `backend/app/middleware/auth.py` — department source

The rule needs `user["department"]`. It was previously sourced **only** from the
Firebase ID token custom claim (`decoded_token.get('department')`, `:145`),
which is fragile if a token lacks the claim. Now:

- `resolve_user_context` reads `UserProfile.department` and adds it to the
  resolved dict when non-empty (kept minimal: the key is omitted when NULL/empty,
  so the hermetic `test_membership_auth.py` shape assertions still hold).
- `get_current_user` prefers the users-row value and falls back to the token
  claim only when the users-row value is empty.

The three real officers already have `department = 'safety'` in the users row, so
the rule is reliable regardless of token freshness.

## 4. Residue deletion (10 users)

The investigation found that the "10 legacy SAFETY_OFFICER users" were **test
residue**, not production users: emails `u-member-*@test.local`, tenant slugs
`rls-op-*`, created by the RLS test helper `backend/tests/_mbb.py:create_user`
(default `role="SAFETY_OFFICER"`). Best-effort test cleanup stranded them.

- Pre-check: `role='SAFETY_OFFICER'` = **10**; non-`@test.local` in the set = **0**
  (no real user affected — the §9 stop condition was not triggered).
- DB: `DELETE FROM public.users WHERE role='SAFETY_OFFICER' AND email LIKE
  '%@test.local'` → **10 rows deleted**. Migration:
  `supabase/migrations/20261017120100_delete_residue_safety_officer_users.sql`.
- Firebase: for each of the 10 synthetic uids, `auth.delete_user(uid)` →
  **10 absent** (they were never Firebase accounts; nothing deleted, 0 failures).
  No Firebase change was made for the three real officers.
- Verify: `role='SAFETY_OFFICER'` = **0**; the three real officers are
  `role='OFFICER', department='safety'`.
