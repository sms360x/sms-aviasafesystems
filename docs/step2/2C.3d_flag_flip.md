## Phase 2 — Flag flip

**DEFERRED.**

Reason: the flag flips every authenticated transaction to the `authenticated`
Postgres role, which is **default-deny** on every table with RLS enabled and no
policy. That set is **10 tables**:

    audit_dispatches, feedback, hazard_assessments, hazard_capas,
    hazard_rca_entries, hazard_rca_factors, invites, psoe_findings,
    memberships, oversight_relationships

Proof (flag ON in a test transaction, `authenticated` role):

```
owner         memberships: 19 rows
authenticated memberships:  0 rows   (query on a zero-policy table is denied)
```

Affected mounted application paths:

    app/routes/feedback.py:77                 Feedback insert (router mounted)
    app/services/psoe_complete_service.py     PsoeFinding read/write
    app/services/users.py:220                 Membership upsert (user creation/update)
    app/repositories/audit_repo.py            AuditDispatch read/write
    app/services/hazard_service.py            hazard_assessments / capas / rca entries+factors

Flipping now would break / degrade:

    - Feedback submission
    - PSOE audit writes
    - User creation (now syncs the memberships reporting substrate)
    - Audit-trail writes
    - SRM assessment persistence
    - the Super-Admin memberships reporting substrate (reads return 0 rows)
    - the regulator-oversight branch (inert while oversight_relationships has no policy)

This is the behavioural-verification stop condition: a legitimate query returns
wrong rows (0) under enforcement.
