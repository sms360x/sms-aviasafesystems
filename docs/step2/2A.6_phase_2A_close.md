## 1. Scope of Phase 2A (as planned)

Phase 2A was the identity and tenancy workstream of Step 2 (workstream W1 in the
Step 2 Plan). Its purpose was to unify the identity and governance model: move
the single `role`/`tenant_id` string on a user to an explicit membership model,
resolve exactly one active context per request at the auth boundary, and place
regulators and service providers under one tenancy model so later workstreams
(roles, RLS, reporting) could build on a single identity. It was the critical-path
phase — the plan's dependency map put W1 ahead of roles (W2) and RLS (W3).

The planned items were: **2A.1** design pass; **2A.2** add the memberships and
oversight tables; **2A.3** backfill one membership per existing user; **2A.4**
switch the auth boundary to resolve from memberships (behind a compatibility
path); **2A.5** tests for parity, negative, cross-tenant, and
middleware-vs-dependency consistency; **2A.6** close. The planning pass added a
findings-driven sub-sequence — **2A.3b** (schema unification of `regulators`
into `tenants`), **2A.3b-code** (ORM single-table inheritance), **2A.3b-cleanup**
(retire `regulators`), and **2A.3c** (service-provider `kind` selector) — because
the plan assumed regulators and operators already shared the `tenants` table,
but the live schema had them in two tables.

## 2. What actually happened

### 2A.1 — Design pass

Read-only design of record (SME-approved 2026-10-10): proposed a
`memberships` table (`user_id`, `tenant_id`, `role`, `effective_from`,
`effective_to`, `is_active`) plus a companion `oversight_relationships` table
(D3/D15), with the auth boundary resolving exactly one active context. The
design permitted **multiple memberships per user** and ranked active rows by
"greatest `effective_from`". This multi-membership assumption was later
corrected (see §3).

### 2A.2 — Add tables

Additive migration `20261010120000_memberships_and_oversight.sql` created
`memberships` and `oversight_relationships` with their indexes (later reflected
in the ORM). Purely additive: no data migrated, no code wired, tables inert,
RLS enabled but not forced, no policies. Public table count 58 → 60.

### 2A.3 — Backfill

Data-only migration `20261010130000_membership_backfill.sql` wrote one
membership per known-role user: **18 memberships created**, matching the
projection (20 users − 2 orphans). Two `STATE_SMD` users with `tenant_id = NULL`
were skipped as orphans and reported as a finding
(`2A.3_orphaned_users.md`). No schema, auth, or code change.

### 2A.3b — Schema unification (regulators into tenants)

Phase 1 of three: added `kind text NOT NULL DEFAULT 'operator'` and 12
regulator-only columns to `tenants`, and inserted the 2 regulator rows
preserving their ids (`caan`, `test-regulator`); `tenants` went 6 → 8. The
`regulators` table was left untouched; no code read the new columns yet.
(Also aligned `tenants.contact_email/phone` types to match `regulators`.)

### 2A.3b-code — ORM unification (STI)

SQLAlchemy single-table inheritance: `Tenant` is the base
(`polymorphic_on=kind`, identity `operator`) carrying all 39 columns, and
`Regulator(Tenant)` is a marker subclass (identity `regulator`). All ORM
read/write paths go through `Tenant`. Added an R3 guard on the demo-purge bulk
delete so a `Regulator` delete cannot touch operator tenants, and made the
`pg_bridge` test fake polymorphic-aware. No schema change.

### 2A.3b-cleanup — Retire regulators

Renamed `regulators` → `regulators_old`
(`20261011130000_rename_regulators_old.sql`); retained with its 2 rows as a
rollback point. Retired the `regulators` CREATE TABLE from `schema_init.py`
(comment/no-op) and updated the RLS coverage test. No reader/writer of the old
table remained.

### 2A.3c — UI changes

Added the service-provider `kind` selector to tenant create/edit in the admin
UI, a `GET /api/v1/admin/tenant-kinds` endpoint, and backend validation of
`kind` on create/update. Removed the legacy "Operator Tenant IDs" field
(oversight is derived from the operator side) and genericised the hardcoded
national examples across the admin pages. No schema or auth change.

### 2A.4 — Auth boundary switch

Integrated the membership resolver into the auth boundary: `resolve_user_context`
read `role`/`tenant_id` from the user's active membership (newest
`effective_from`), with no fallback, and user creation wrote a membership. The
`get_current_user`-override test pattern replaced the old Firebase-token
mocking. **The multi-membership design was still assumed here**; the design
error was latent and was not caught until 2A.5.

### 2A.5 — Memberships repurposed; auth boundary reverted

The test pass built the situations the design assumed and **two tests failed**,
revealing that the resolver did not implement the design's own rules (G9, G12;
see §3). SME review on 2026-10-12 corrected the rule to **one user = one tenant
= one role**, and the auth boundary was **reverted to read from the `users`
row**. The `memberships` table was retained but **repurposed** as the
Super-Admin reporting substrate, kept in sync on user creation and role change,
with a new `memberships_one_active_per_user` unique index. This is a partial
revert of 2A.4.

### 2A.6 — This close document

Records the phase: intent, actual execution, the design error and recovery, the
resulting invariant set, what is deferred, and what Phase 2B inherits. No code,
schema, or tests.

## 3. The design error and the recovery

### The wrong assumption

The 2A.1 design pass recorded that a user could belong to more than one tenant
("multi-membership per user"), with several effective-dated memberships and a
resolver that ranked them by `effective_from`. This was based on a reading of
the requirements, not on the ICAO accountability structure. The resolver was
built (2A.4) around that assumption.

### How it was caught

The 2A.5 test pass created the situations the design assumed would exist. Two
tests failed:

- **G9** — a future-dated membership (`effective_from` in the future) was
  chosen as the current context; the resolver did not filter on
  `effective_from`, it only filtered on `is_active` and `effective_to IS NULL`.
- **G12** — an explicit tenant request was ignored; the `tenant_id` parameter
  was accepted by `resolve_user_context` but never read.

Both tests were correct. Both revealed that the resolver did not implement the
design's own rules.

### The SME correction

SME review on 2026-10-12 established the correct rule:

    One user = one tenant = one role.
    A person acting for two organisations has two separate user records
    in the application.
    Multi-membership is forbidden under the ICAO accountability structure.

### The recovery

The auth boundary was reverted to read `role` and `tenant_id` from the `users`
row (`resolve_user_context` no longer queries memberships). The `memberships`
table was retained, but repurposed as the Super-Admin reporting substrate and
kept in sync on creation and role change. The two defects (G9, G12) are **moot
under the corrected model**, since the code path they were in — membership
selection with effective dates — no longer exists.

### The lesson

The test pass is what revealed the wrong design assumption. Without 2A.5, the
wrong design would have shipped.

## 4. The invariant set (what is now true)

- One user = one tenant = one role. Represented by the single-valued
  `users.tenant_id` and `users.role` columns and written by the user-creation
  path.
- One active membership per user. Enforced by the unique index
  `memberships_one_active_per_user`.
- The auth boundary reads from the `users` row. It does not read from
  `memberships`.
- The `memberships` table is the Super-Admin reporting substrate. It is kept in
  sync on user creation and role change and is not read by any operational code
  path.
- Regulators and service providers both live in `tenants`, distinguished by
  `kind`.
- The `regulators` table is retired (`regulators_old` retained for one cycle).
- `oversight_relationships` exists for regulator-to-operator oversight
  (currently 0 rows).
- The ORM uses single-table inheritance (`Tenant` base + `Regulator`
  subclass).

## 5. What is deferred

- **The Super-Admin dashboard.** Queries `memberships` for cross-tenant reports.
  Not built in Phase 2A.
- **The reporting endpoint `GET /api/v1/admin/memberships`.** Deferred with the
  dashboard.
- **The `regulators_old` drop.** Retained for one cycle; to be dropped in a
  later cleanup.
- **The role model unification (Phase 2B):** `STATE_SMD` canonical
  (`CAAN_SMD` retired), `SAFETY_OFFICER` → `OFFICER`, `AIRLINE_ADMIN`
  decommissioned.
- **The RLS enforcement (Phase 2C):** policies rewritten against the app
  identity; `FORCE ROW LEVEL SECURITY` or non-owner-role decision.
- **The durable audit trail (Phase 2E).**
- **The placeholder removal (Phase 2F).**

## 6. What Phase 2B inherits

- The identity model is stable and correct (one user = one tenant = one role;
  auth boundary reads the `users` row).
- The role model is unchanged (still has legacy names: `CAAN_SMD`,
  `SAFETY_OFFICER`, `AIRLINE_ADMIN`).
- Three conflicting role sets remain (per 1C.1b-i): `_RAW_VSR_ROLES`,
  `CUSTODIAN_ROLES`, `REPORT_VIEWER_ROLES`.
- The closure-path defect (`get_accountable_executive` does not admit the
  canonical `ACCOUNTABLE_EXECUTIVE` role) remains unfixed (per 1C.2 residual).
- The tenancy model (`kind`, `oversight_relationships`) is in place.
- The test harness is functional; known failures are recorded.

## 8. What Phase 2A achieved, in one paragraph

Phase 2A unified the identity and tenancy model. Regulators and service
providers now live in one table (`tenants`) with a `kind` column. The auth
boundary reads from the `users` row and uses the correct rule: one user = one
tenant = one role. A `memberships` table remains as the Super-Admin reporting
substrate. The design was corrected mid-phase after tests revealed the wrong
assumption, and the implementation was reverted and repurposed. The result is a
simpler identity model than the one the plan originally proposed.
