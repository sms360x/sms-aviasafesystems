### 1.1 What was wrong

* **3 OFFICER accounts carried no `department` claim at all**
  (`safety@sitaair.com.np`, `safety@saurya.com.np`, `safety@air-dynasty.com.np`).
  Under RBAC_MODEL §4 an OFFICER is only a *Safety Officer* when it belongs to
  the Safety department; every other officer falls back to the least-privilege
  employee profile. With no claim the account was **fail-closed** — no Safety
  persona, no Safety dashboard, no Safety Manager rights.
* **7 accounts carried a legacy free-text claim** (`"Part 145/AMO"`,
  `"Flight Operations"`, `"Corporate Safety Department"`, …) instead of a
  canonical department code, so the department-scoped rules could not match
  them either.

The **`users` mirror row was already correct** in every case (it holds the
canonical code), which is what RBAC_MODEL makes authoritative — the token
claim was the only lagging part.

## 2. Fail-closed behaviour — confirmed before and after

The rule (`backend/app/core/rbac.py`):

```python
is_safety_officer(user)  # OFFICER only when department ∈ {safety, corporate_safety}
normalize_legacy_role("OFFICER", None)  -> "employee"   # fail-closed
```

Measured with a freshly minted ID token for
`safety@air-dynasty.com.np` (a real sign-in: a custom token **without**
claims, so the stored custom claims are what the browser receives):

| | Before (no claim) | After (claim = `safety`) |
|---|---|---|
| ID-token `department` | *(absent)* | `safety` |
| `is_safety_officer(user)` | `False` | **`True`** |
| Normalised RBAC profile | `employee` (fail-closed) | **`safety_manager`** |
| Front-end nav persona (`getUserRoleType`) | `ALL` | **`SAFETY`** |

The backend already resolved the department from the authoritative `users`
row, so the backend-side Safety-Officer decision was correct before the fix;
what the missing claim broke was the **token/front-end** side (the nav
persona and any client that reads the claim).

## 3. Defects found while running the checklist

### 3.1 `PATCH /api/v1/admin/users` answers 500 under RLS enforcement (pre-existing)

`backend/app/routes/admin.py::admin_update_user` performs, in this order:

1. `auth.update_user(uid, custom_claims=…)` — the Firebase claim write,
2. `upsert_user_doc(...)` — the `users` mirror refresh,
3. `log_audit(action="USER_UPDATED", …)` — the audit event.

Step 2 fails with

```
asyncpg.exceptions.InsufficientPrivilegeError:
new row violates row-level security policy for table "users"
```

because `public.users` has RLS enabled with a single **read** policy
(`user_read_own`) and **no permissive write policy for a platform role** —
a `SUPER_ADMIN` identity (no tenant) may not write a mirror row for a
tenant. The endpoint therefore answers **HTTP 500**, *after* the claim was
written and *before* the audit event is written.

Consequences:

* The claim **is** applied (step 1 already ran) — which is why the re-audit
  shows 0 missing / 0 invalid.
* The mirror is unchanged (its value was already correct).
* The `USER_UPDATED` audit event was **not** written.

Scope: pre-existing Phase 2B code, not introduced by Task 2. The same
defect will affect every admin endpoint that refreshes a `users` mirror row
(claim changes, display-name changes, provisioning).

Not fixed in this task — it needs a decision on the `users` write path
(a platform-scoped write policy, or a SECURITY DEFINER upsert like the one
`set_tenant_config_key` uses for tenants).

**Mitigation used for this checklist:** the 10 missing `USER_UPDATED` events
were backfilled onto the durable trail with
`metadata.source = "ops-department-claim-backfill"` and
`metadata.backfilled_audit_event = true`, so the trail is complete and the
backfill is itself visible in the console.

### 3.2 The 2E.2 backfill fork — reported, not repaired

See §3.4 of `docs/step3/3A.2_super_admin_console_design.md`: the historical
backfill shares one timestamp, so the historical chains contain forks. The
console reports it (`status: broken`, fork counts); it does not repair it —
repair would mean rewriting append-only rows.

## 4. Reproduction

```powershell
# audit (read-only)
python backend/scripts/audit_department_claims.py

# audit + JSON snapshot
python backend/scripts/audit_department_claims.py --json claims.json

# populate through the admin API
python backend/scripts/audit_department_claims.py --apply --api-base http://127.0.0.1:8099

# backfill the audit events the API could not write
python backend/scripts/audit_department_claims.py --record emails.txt
```

`--api-base` points at a **local** backend instance: the deployed instance
uses a different `SETUP_SECRET` than the development environment, so the
setup-key second factor cannot be satisfied against it from here.
