## 1. Scope

Phase 3A Task 2 delivers a **SUPER_ADMIN-only console** with two surfaces:

| Surface | What it does | Mutating? |
|---|---|---|
| **Audit Chain Viewer** (`/admin/audit-chain.html`) | Read-only inspection of the durable, per-tenant HMAC hash chain (`public.durable_audit_logs`): per-tenant chain status, filtered/paginated event list, per-event detail with the chain link and a server-computed integrity verdict. | **No** |
| **System Configs** (`/admin/system-config.html`) | View/edit of a fixed inventory of permitted configuration keys (tenant feature flags + tenant survey settings), plus read-only platform configuration. | **Yes — audited** |

Both are gated to `SUPER_ADMIN` at the backend route level *and* at the
frontend route/nav level. No service-role key, no HMAC key and no
platform secret reaches the browser.

## 2. Backend surface

### 2.1 Audit Chain Viewer — `backend/app/routes/audit.py`

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/v1/audit/verify?tenant_id=<slug>` | Pre-existing chain check (unchanged semantics: `{"valid": true}` / `{"valid": false, "broken_at_id": …}`). |
| GET | `/api/v1/audit/events` | Filtered, paginated event list. Filters: `tenant_id`, `action`, `actor_role`, `date_from`, `date_to`, `verification`, `limit`, `offset`. |
| GET | `/api/v1/audit/events/{id}` | One event: type, timestamp, actor role + pseudonymous fingerprint, tenant label, payload summary, `prev_hash → current_hash` link, predecessor id, successor count, verdict. |
| GET | `/api/v1/audit/tenants` | Per-tenant chain summary: event volume, chain segments, forked links, dangling links, `valid`/`broken` status. |

Every route is `Depends(get_admin_user)` → **403 for any non-`SUPER_ADMIN`
identity**. The router exposes **no** `POST`/`PUT`/`PATCH`/`DELETE` route —
asserted by a test that walks `app.routes`.

Cross-tenant reads are permitted for `SUPER_ADMIN` and are explicitly
labelled: each row carries `tenant_slug`, `tenant_name` and `tenant_label`,
and the list response carries `cross_tenant: true` when no tenant filter is
applied.

## 3. Audit verification approach

### 3.1 What is signed

`append_audit_event()` (SECURITY DEFINER) signs

```
prev_hash || action | resource_type | resource_id | metadata::text | actor_uid
```

with HMAC-SHA256 and stores the hex digest in `current_hash`. The chain is
per tenant partition (`uuid5('tenant:' + slug)`); tenantless events live in
the `__global__` partition.

### 3.2 Two verdicts, deliberately

| Verdict | Meaning | How it is computed |
|---|---|---|
| `valid` | The stored digest recomputes **and** the row's predecessor exists in the same partition. | `pgcrypto.hmac(...) = current_hash` **and** `EXISTS (predecessor with current_hash = prev_hash)` |
| `broken` | The stored digest does **not** recompute — the signed body was altered. | `hmac(...) IS DISTINCT FROM current_hash` |
| `unlinked` | The digest recomputes but the predecessor row is missing — the row was separated from its chain. | `prev_hash <> 'GENESIS'` and no predecessor row |

The verdict is computed **server-side only**. The client receives a status
string; it never receives the HMAC key, a salt, or enough material to
recompute a digest itself.

`verify_durable_chain()` (the Phase 2E.2 SQL function) is **unchanged** — its
tested semantics are preserved. The viewer adds a *read-side* integrity model
on top of it: the SQL function answers "does the chain verify?", the viewer
answers "which event does not?".

### 3.3 Chain-level status

The per-tenant summary reports structure, not just row verdicts:

* **chain_segments** — rows with `prev_hash = 'GENESIS'` (chain roots). More
  than one means the partition was never a single chain.
* **forked_links** — `prev_hash` values with more than one successor. A fork
  means the ordering after that point is ambiguous.
* **dangling_links** — rows whose predecessor is missing.

`status` is `valid` when `forked_links + dangling_links = 0`, otherwise
`broken` (with a human-readable `status_detail`).

### 3.4 Known pre-existing defect — forked backfill (NOT introduced here, NOT repaired here)

The 2E.2 backfill wrote 5 837 historical rows with **one shared transaction
timestamp**. `append_audit_event()` picks the head with
`ORDER BY timestamp DESC, id DESC`, so the backfilled rows chain to an
*arbitrary* predecessor and the historical chains contain forks
(1 202 `GENESIS` rows globally; the `__global__` partition has 1 root and
25 successors on one link).

Observed on the live trail (6 893 rows):

* Every row's **own** digest recomputes → all rows are `valid` at row level.
* The **structure** is forked → affected partitions report `status: broken`
  with a fork count.

This is reported by the console rather than silently repaired. Repairing it
would require re-writing or deleting append-only rows — exactly what the
Phase 2E.2 design forbids. The remediation options (re-backfill with strictly
increasing timestamps into a fresh partition, or accept the historical
partition as "legacy, read-only") are a decision for the SME, not a code
change in this task.

## 4. Config key inventory

Only the keys below are editable. Anything else is rejected with `404`
(unknown key) or `400` (read-only / invalid value).

### 4.1 Feature flags — target `tenants.modules` (legacy `module1..module4`)

| Canonical key | Storage | Type | Notes |
|---|---|---|---|
| `module_a_survey` | `module1` | bool | Module A — SMS maturity assessment. |
| `module_b_srm` | `module2` | bool | Module B — hazard & risk (SRM). The CAN/CAP add-on inherits this flag. |
| `module_c_regulator` | `module3` + `module4` | bool | Module C — PSOE audit + regulator dashboard. |
| `module_b_can_cap` | *(derived)* | bool | **Read-only.** Derived from `module_b_srm`, exactly as the shell derives it (`public/js/nav-config.js`). |

### 4.2 Tenant settings — target `tenants.data->'config'` (+ derived `surveyConfig` mirror)

| Canonical key | Type | Validation |
|---|---|---|
| `survey_rate_limit` | int | one of 5 / 10 / 25 / 50 / 100 (`SURVEY_RATE_LIMIT_OPTIONS`). |
| `survey_open_date` | date | `YYYY-MM-DD`; empty string clears the field. |
| `survey_close_date` | date | `YYYY-MM-DD`; must be after the open date; empty clears. |
| `is_survey_active` | bool | Manual override of the derived open/closed state. |
| `survey_instructions` | text | ≤ 2 000 characters. |

**Clearing a value.** `value: null` is the explicit *clear* request: the key
is set to a JSON null in the tenant's config map (the date fields are removed
instead, following the tenant-config merge semantics), so the platform default
applies again. The console renders an empty control as "not set (platform
default)". The clear is audited exactly like a set — `SYSTEM_CONFIG_UPDATED`
with `value: null`.

The merge semantics are **not** re-implemented: the console reuses
`tenant_service.build_config_update()` for validation and for the derived
camelCase `surveyConfig` mirror, and the write itself happens inside
`set_tenant_config_key()` (see §5.2).

### 4.3 Platform configuration (read-only visibility, never editable)

Canonical roles, canonical department codes, cross-tenant roles, environment,
RLS enforcement posture and the audit-chain policy (storage, write path, read
access, "no mutation path exists"). No secret is exposed — the view states
only *whether* an HMAC key is configured, never its value.

## 5. Write path, auditing and access control

### 5.1 Database objects (migration `20261022170000_super_admin_console.sql`)

1. **`durable_audit_logs.actor_role`** — nullable text: the role the actor
   held when the event was appended. It is **evidence recorded alongside**
   the event, not part of the signed body, so every chain that exists today
   still verifies byte-for-byte.
2. **`append_audit_event(..., p_actor_role, ...)`** (8-arg) — the writer now
   records the role. The **7-arg form is kept as a thin wrapper** (role =
   `NULL`) so an application deployed before/after the migration keeps
   appending successfully.
3. **`admin_tenant_view()`** — SECURITY DEFINER read view
   (slug, name, tenant_uuid, kind, status, module flags, config, survey
   config). It exists because the `tenants` table is **not readable by
   platform roles** under the app's RLS identity (its policies are
   tenant-scoped), so the console needs a definer path to label audit rows
   and to list tenant configuration.
4. **`set_tenant_config_key(...)`** — SECURITY DEFINER write path: merges one
   permitted key into the tenant row (keeping every undeclared key), syncs the
   derived mirror, and appends the `SYSTEM_CONFIG_UPDATED` event **in the
   same transaction**, so a configuration change can never land un-audited.

### 5.2 Defence in depth

Both definer functions carry an internal gate —
`current_setting('app.current_role') IS DISTINCT FROM 'SUPER_ADMIN'` →
`RAISE ... ERRCODE '42501'`. Because they bypass RLS, the gate has to live
inside them. The application-level `get_admin_user` dependency is the first
line; the database gate is the second. A test drives the service with a
`TENANT_ADMIN` identity and asserts the database refuses the write.

### 5.3 Layered access control

| Layer | Mechanism |
|---|---|
| Backend route | `Depends(get_admin_user)` → `SUPER_ADMIN` only (403 otherwise). |
| Write second factor | `verify_setup_key()` — the same `SETUP_SECRET` used by the existing admin provisioning endpoints. |
| Database | `app.current_role = 'SUPER_ADMIN'` checked inside both definer functions. |
| Frontend page | `AdminUI.requireAdmin()` — redirects non-`SUPER_ADMIN` users. |
| Frontend nav | The two new nav entries carry `roles: ['SUPER']`; every other role type (SAFETY, CAAN, AE, DEPT_ADMIN, ALL) is filtered out. |

### 5.4 Actor role capture

`log_audit()` gained an optional `actor_role` argument. When it is not
supplied, the role is taken from the **request-scoped RLS identity**
(`app.db.rls.get_current_identity()`), so every request-scoped event records
the capacity the actor acted in without touching the call sites. Anonymous VSR
actions (`VSR_SUBMITTED`, `REPORTER_CONTACT_*`) never carry an actor or a
role.

## 6. Data protection

* **The HMAC key never leaves the server.** It is read from the environment
  (`AUDIT_HMAC_KEY`) inside the service layer; the API returns verdicts only.
  A test asserts the key literal does not appear in any response body.
* **Actor identity is pseudonymous.** The viewer returns
  `actor_fingerprint` (the first 12 hex chars of `sha256(actor_uid)`) plus
  `actor_role`. The raw `actor_uid` is not in the payload at all.
* **Payload redaction (second layer).** The write side already strips PII
  from anonymous VSR events; the viewer additionally masks anything that
  *looks* like PII: values under `email / phone / ip / reporter / passport /
  national_id / contact` keys become `[redacted]`, e-mail patterns become
  `[redacted-email]` and phone-like numbers become `[redacted-phone]`.
* **No reporter reconstruction.** The console shows the audit *record* of a
  reporter contact event (that it happened, when, by whom) — never the
  reporter's identity. `reporter_contacts` is not readable through any
  console route.
* **The service-role key is never exposed to the client.** All console reads
  and writes go through the backend's own database credentials.

## 7. Explicit non-goals

These are **deliberately absent**, not "not yet implemented":

1. **No mutation of `durable_audit_logs`** — no update, delete, reorder,
   backfill, re-hash or "repair chain" endpoint. The append-only trigger
   (`durable_audit_no_mutate_trg`) is untouched and a test asserts that
   `UPDATE`/`DELETE` on the table still raise.
2. **No editing of `reporter_contacts`** and no exposure of reporter PII.
3. **No impersonation / break-glass** into tenant data. `SUPER_ADMIN` reads
   across tenants; it does not act as a tenant user.
4. **No tenant lifecycle management** (status changes, provisioning, user
   administration) — those stay in the existing admin endpoints.
5. **No export of the audit trail** (no CSV/JSON dump) in this phase.
6. **No platform-secret editing** — the platform configuration is visible,
   never writable.
7. **No repair of the forked historical backfill** (§3.4) — reported, not
   rewritten.
8. **No new roles.** The console uses the existing `SUPER_ADMIN` role and the
   existing `SETUP_SECRET` second factor.

## 9. Known limitations and reported defects

| Item | Status |
|---|---|
| The 2E.2 backfill left forked historical chains (§3.4). | **Reported**, not repaired — repairing would mean rewriting append-only rows. The console shows the fork counts and `status: broken`. |
| `PATCH /api/v1/admin/users` answers **HTTP 500** under RLS enforcement: the `users` mirror upsert has no permissive write policy for a platform role, so the endpoint fails *after* the Firebase claim was written and *before* the audit event. | **Pre-existing** (Phase 2B code, not introduced here). Found while running the Parallel Ops Checklist; see `docs/step3/3A.2_ops_log.md` §3.1. A fix needs a decision on the `users` write path (a platform-scoped write policy, or a SECURITY DEFINER upsert like `set_tenant_config_key` for tenants) — out of Task 2's scope. |
| The console can set and clear every permitted key, but it cannot create or delete **tenants**, and it cannot change a tenant's lifecycle `status`. | **Non-goal** (§7.4). |
| The console pages the trail with a server-side integrity verdict; the first page of a cross-tenant view over ~7 000 rows takes a few seconds against a remote database (the HMAC pass is per row). | Accepted for an admin surface; the ordinary path paginates first and verifies only the rows on the page, and a verdict filter is an explicit forensic query over the whole filtered set. |
