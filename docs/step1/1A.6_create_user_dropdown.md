## Background

the same effective role: `CAAN_SMD` and `STATE_SMD` (the UI maps
`STATE_SMD -> CAAN_SMD` at the auth boundary). The SME ruled: keep **State SMD**,
remove the stale **CAAN SMD** option. The backend continues to accept `CAAN_SMD`
as a legacy value until Step 2.

## Residuals

- **Edit modal preselect edge case:** `openEditUserModal` assigns the current
  role string to `#editUserRole`. A legacy account whose role is `CAAN_SMD` (not
  `STATE_SMD`) will no longer match an option, so the select shows blank until
  the admin picks a role. This is inherent to removing the option as
  directed; admins should re-select "State SMD (Regulator)" for such accounts.
  Backend still accepts `CAAN_SMD`, so no request is broken. Not in scope for
  1A.6.
- Post-push visual verification is required (above).

## Residual: legacy CAAN_SMD accounts

Removing the CAAN_SMD option from the Edit User role dropdown (line 235)
means existing accounts whose stored role is CAAN_SMD will open with a
blank role select until the Super Admin re-selects "State SMD
(Regulator)".

This is a direct consequence of the L4 finding (the code normalises
STATE_SMD inward to CAAN_SMD; the stored value for regulator users is
CAAN_SMD while the UI label is "State SMD").

Resolution path: the L4 refactor in Step 2 will migrate stored claims
from CAAN_SMD to STATE_SMD. Once migrated, the Edit dropdown and the
stored value will align.

Step 1 status: residual documented. No code change in 1A.6 beyond the
two-line removal already committed (7336e19).

Pilot mitigation (optional, not applied): the Super Admin should
re-select "State SMD (Regulator)" when editing any existing regulator
user account. A note to this effect is to be included in the admin
handover for the pilot.
