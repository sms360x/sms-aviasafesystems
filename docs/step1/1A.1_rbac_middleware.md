## Finding

`SECURITY_REVIEW.md` (2026-09-18) finding **M5** states the RBAC/tenant-isolation middleware is never registered. That review is **stale** — the middleware is registered in the current code:

- `backend/app/main.py:123-127`:
  `# RBAC module-access + tenant-isolation gate (P2-26). Registered last so it runs ...`
  `from app.middleware.rbac_middleware import RBACMiddleware`
  `app.add_middleware(RBACMiddleware)`

## What the middleware does

`backend/app/middleware/rbac_middleware.py`: maps request paths to modules (`ENDPOINT_MODULE_MAP`), normalizes legacy roles via `app/core/rbac.py`, rejects a role lacking module permission (403), rejects a disabled tenant module flag (403), and blocks a tenant user from a path whose `tenant_id` differs from their session (403). Cross-tenant roles (`CAAN_SMD`, `SUPER_ADMIN`) bypass the module gate but not tenant isolation.

## Action taken

No new security code and no new test were written: this finding is already fixed and a regression test already exists. The plan's "verify + regression test" was satisfied by running the existing suite.

## Review outcome (2026-10-07)

Review of the initial 1A.1 closure found the existing tests were unit-level only (they monkeypatch `_user_from_request` and use an internal sentinel), with no real-route integration assertion. This was corrected.

- The middleware is a **module gate, not an authentication gate**. Authentication is enforced by per-route dependencies (`get_current_user` / `get_caan_user`), not by the middleware. The middleware intentionally passes unauthenticated requests through (`test_unauthenticated_passthrough`).
- **Token-level rejection** (missing / invalid / expired / revoked tokens) is **not** tested here and is deliberately deferred to **1A.2** (SPI routes) and **1A.3** (N-HRC routes), where route-level auth dependencies are the correct subject.
- Two **integration tests** were added to close the "no real 200" and "no real 403" gaps, both driving the real FastAPI app over the mapped route `GET /api/v1/sms-maturity/{tenant_id}/cache` (module1):
  - `test_integration_valid_own_tenant_returns_200` — valid own-tenant TENANT_ADMIN, module enabled → asserts **200** and that it is not a middleware 403.
  - `test_integration_module_disabled_returns_403` — valid TENANT_ADMIN, tenant module flag off → asserts **403**.
  - Placement decision: added to `backend/tests/test_rbac_middleware.py` (same file). It is the RBAC-middleware test module; a sibling file was unnecessary, and the unit and integration tests are deliberately kept together.
- The unit tests remain; the integration tests complement them.
- Closing condition: all tests in the file pass, plus the full suite.

The RBAC middleware gates only paths whose prefix is in `ENDPOINT_MODULE_MAP`. As of HANDOFF_GUIDE.md 2026-10-01, `/api/v1/dashboard*` is NOT in that map. The four dashboard hubs therefore render module-tagged data without a module gate. This is a pre-existing gap. It is now in scope for item 1A.4, which will add `/api/v1/dashboard` to the map (or document why it cannot be added safely).
