## 1. Summary

The live `public` schema holds **58 tables**. RLS is **enabled on all 58**
(`relrowsecurity = true`) and **forced on none** (`relforcerowsecurity = false`).
There are **57 policies** across **48 tables**; **10 tables have RLS enabled
with zero policies** (default-deny for any non-owner role): `audit_dispatches`,
`dead_letter_queue`, `feedback`, `hazard_assessments`, `hazard_capas`,
`hazard_rca_entries`, `hazard_rca_factors`, `invites`, `psoe_findings`,
`sms_dispatches`. Every table is owned by the `postgres` role, and the backend
connects as that same `postgres` (Supabase pooler user
`postgres.bftnwljnpnpniksmalnk`) — so **RLS is bypassed on the application path**
(the owner is exempt unless a table is `FORCE ROW LEVEL SECURITY`, which none
are). Additionally, every live policy predicate reads Supabase GoTrue claims
(`auth.jwt()`, `auth.uid()`) or `current_setting('app.current_tenant')`, none of
which the Firebase-authenticated app path ever presents — a second, independent
reason the policies cannot enforce on the app path. Per the 1B.2 plan, the
platform-wide tables to **exempt** are `dead_letter_queue`, `sms_dispatches`,
`audit_dispatches` (plus, by registry nature, `tenants`). Tenant isolation is
presently provided by application code, not the database (see
`docs/step1/rls_bypass_finding.md`).

## 6. RLS bypass detail

- **Backend connection user:** `postgres` (`current_user = postgres`,
  `session_user = postgres`, `current_database = postgres`). Logged-in pooler
  user is `postgres.bftnwljnpnpniksmalnk` at
  `aws-0-ap-southeast-1.pooler.supabase.com:6543` (Supabase transaction pooler).
  Password is not recorded here. (`backend/app/db/session.py`;
  `backend/app/core/config.py:92-104`; `backend/.env`.)
- **Table owner:** `postgres` for **all 58** tables — i.e. the connection user is
  the table owner. Postgres RLS does not apply to the table owner unless the
  table is `FORCE ROW LEVEL SECURITY`.
- **`rls_forced`:** `false` on **all 58** tables.
- **Policy predicates:** all live policies read `auth.jwt()` /
  `auth.uid()` (Supabase GoTrue claims) or `current_setting('app.current_tenant')`
  — none is set by the Firebase-authenticated backend. So even if the connection
  were not the owner, the policies would evaluate against absent claims.
- **Non-owner code paths:** **none found** in application code. No `SET ROLE`,
  no service-role SQLAlchemy engine, no `set_config('app.current_tenant')` on the
  app path. The service-role / BYPASSRLS assumption is confined to the one-off
  migration script `scripts/migrate_firestore_to_supabase.py:1357`.
- **Effect:** the `postgres` owner connection bypasses RLS on every table; tenant
  isolation on the app path is enforced only by application code (section 4b).
