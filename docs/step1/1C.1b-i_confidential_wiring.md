# 1C.1b-i — Confidential reporting service wiring (STOPPED)

PHASE: 1C
ITEM: 1C.1b-i — wire `confidential_reporting_service` into the VSR path
STATUS: **STOPPED** (integration point ambiguous; role-model conflict) — no code changed
DATE: 2026-10-10
BRANCH: step1-audit-readiness

Per instruction Section 2.3 / Section 8: the integration point cannot be
determined from the code, and `can_view_reporter_identity` contradicts the 1C.1
raw-access rule across three conflicting role models. The service was **not
wired**. This document records the finding. No schema, endpoint, raw-access, or
cross-tenant change was made.

## 1. Validation results

### 1.1 `ConfidentialReportingService` public methods

File: `backend/app/services/confidential_reporting_service.py`.

| Method | Signature | Does | Expects | Returns | DB write |
|---|---|---|---|---|---|
| `mark_confidential` | `(report_id: str, custodian: dict, user: dict)` | sets `is_confidential=True`, `confidential_custodian_id=resolve_actor_uuid(custodian)`, `updated_at`; audits `REPORT_MARKED_CONFIDENTIAL` | a custodian **user dict** (uid/email) | `{id, is_confidential, confidential_custodian_id}` | **yes** (existing columns) |
| `can_view_reporter_identity` | `(report, user)` | True if report not confidential; True for `SUPER_ADMIN`; else only `CUSTODIAN_ROLES` when actor == custodian (or custodian is null) | report (row/dict) + user | bool | no |
| `deidentify` | `(report)` | nulls `reporter_name/email/phone/role/organisation`, sets `is_anonymous=True`, `reporter_identity_protected=True` | report | dict | no |
| `get_for_downstream` | `(report_id: str, user)` | loads row; if confidential and not `can_view_reporter_identity` → audit `CAAN_READ_REPORT_DEIDENTIFIED` + `deidentify(row)`; else raw dict | report_id + user | dict / None | no |

The service is referenced only by `tests/test_confidential_reporting.py`.

### 1.2 Submission path

`backend/app/routes/occurrence_reports.py`:

- `submit_report` (`POST /`), `submit_mor` (`/mor`), `submit_vsr` (`/vsr`) all
  create the row through `ReportService.create_report`.
- **None** call `mark_confidential` or `deidentify`.
- Reporter metadata is stored on the **same `reports` row**
  (`reporter_name/role/email/phone/organisation`), not split.
- A VSR additionally auto-creates a hazard (`_auto_create_hazard_from_report`),
  which copies `narrative` into the hazard title/description and carries **no**
  reporter-identity columns.

### 1.3 Read path

- `get_reports` (list) composes with `_to_list_item`; `get_report` (detail)
  composes with `_to_report_response` (narrative + reporter metadata).
- After 1C.1 + correction, a non-raw same-tenant caller is **403** before any
  composition; a cross-tenant VSR is **404** (1A.7).
- A `deidentify` / `get_for_downstream` call would belong after the raw-access
  check, but no caller remains who is "non-raw yet legitimate": 1C.1 denies them
  outright and 1A.7 excludes cross-tenant VSRs.

### 1.4 Role-model conflict (material)

| Source | Set | Notes |
|---|---|---|
| `occurrence_reports._RAW_VSR_ROLES` (1C.1) | `{AIRLINE_ADMIN, TENANT_ADMIN, SAFETY_OFFICER}` | raw VSR access |
| `confidential_reporting_service.CUSTODIAN_ROLES` | `{TENANT_ADMIN, AIRLINE_ADMIN, SUPER_ADMIN}` | **omits SAFETY_OFFICER**, adds SUPER_ADMIN; per-user custodian matching |
| `master_register.REPORT_VIEWER_ROLES` | `{TENANT_ADMIN, SAFETY_OFFICER, OFFICER, SUPER_ADMIN}` | **omits AIRLINE_ADMIN**, adds OFFICER; comment at `master_register.py:37-38` states `is_confidential` is **dormant and must NOT be used for gating** |

`can_view_reporter_identity` therefore **contradicts** `_RAW_VSR_ROLES`: the
1C.1 correction grants `SAFETY_OFFICER` raw VSR access, while the service would
return identity to a `SAFETY_OFFICER` as **de-identified** (or, for confidential
rows with a custodian, deny). The three sets are mutually inconsistent and no
single source of truth exists in code.

### 1.5 Existing tests

`backend/tests/test_confidential_reporting.py` asserts, at unit level:

- `mark_confidential` sets `is_confidential=True` and the resolved
  `confidential_custodian_id`.
- `can_view_reporter_identity` is True for the `AIRLINE_ADMIN` custodian and
  False for a `SAFETY_OFFICER`.
- `get_for_downstream` nulls `reporter_name`/`reporter_email` and sets
  `is_anonymous=True` for a `SAFETY_OFFICER`.

Wiring that honours 1C.1 (SAFETY_OFFICER raw) contradicts the second/third
assertions; wiring that honours the service violates the 1C.1 correction. The
existing tests do not break from a no-op (unwired) state.

### Where the service should be called

**Indeterminate.** There is no reachable "de-identified" caller on the read
path (1C.1 returns 403 for non-raw same-tenant callers; 1A.7 returns 404 for
cross-tenant VSRs), and the submission-side `mark_confidential` has no
designated Safety Department custodian to resolve.

## 2. Integration point chosen and why

**None.** Per Section 2.3 no integration point was chosen. Reasons:

- Read path: `get_for_downstream` would be a no-op (no non-raw legitimate
  caller), and honouring it would require changing the 1C.1 raw rule (forbidden
  by Section 2.4).
- Submission path: `mark_confidential` needs a custodian user resolved from the
  Safety Department; no such custodian is derivable from the code, so wiring it
  requires a design decision (custodian source) — deferred to 1C.1b-ii.
- Submission-side `deidentify` would strip identity from the Safety
  Department's own working copy and is not required (the downstream hazard
  register already carries no reporter-identity columns).
- `master_register` explicitly warns that `is_confidential` is dormant and must
  not be used for gating, contradicting a gate built on the service's flag.

## 6. Open gaps

- **Reporter-contact store (schema)** — deferred to **1C.1b-ii**. There is no
  separate location for VSR reporter contact details; they are columns on the
  `reports` row (`db_models.py:259-263`). Closing this requires a schema change

- **AE aggregate view (VSR counts only)** — deferred to **1C.1b-iii**. No
  dedicated AE VSR aggregate endpoint exists (see
  `docs/step1/1C.1_vsr_visibility.md` §4).
- **Role-model reconciliation** — a Step 2 decision: unify `_RAW_VSR_ROLES`,
  `CUSTODIAN_ROLES`, and `REPORT_VIEWER_ROLES` (and retire `SAFETY_OFFICER` in
  favour of `OFFICER` + department). Until then, wiring the service onto the
  VSR path would encode an unreconciled model.

## 7. Conclusion

The `confidential_reporting_service` is **not** wired into the VSR path. The
item stopped before changing code because the integration point is
non-determinable on the current code and the service's identity-visibility role
check conflicts with the 1C.1 raw-access rule. No schema, endpoint, raw-access,
or cross-tenant change was made.
