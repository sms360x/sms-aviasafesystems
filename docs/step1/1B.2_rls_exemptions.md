## 1. Platform table exemptions

Two tables are exempted from RLS policy development. They are
platform infrastructure, not tenant-owned data.

### dead_letter_queue
    Classification: platform.
    Holds: failed job payloads pending investigation.
    tenant_id column: none.
    Why exempt: infrastructure queue. Reads are done by
    platform operators, not tenants.
    Access rule: platform operators.
    Condition under which RLS would be required: if tenants
    ever see their own failed jobs, RLS with a tenant_id
    filter is required.

### sms_dispatches
    Classification: platform.
    Holds: SMS delivery records for dispatch jobs.
    tenant_id column: present (tenant_id text, with an index
    ix_sms_dispatches_tenant).
    Why exempt: dispatch infrastructure. No tenant-facing
    read path found in app code; the tenant_id column is
    currently dormant.
    Access rule: platform operators.
    Condition under which RLS would be required: if a
    tenant-facing read path for sms_dispatches is added,
    RLS with a tenant_id filter is required.

## 2. Deferred tenant-owned policies (Step 2)

Eight tables have RLS enabled but no policies. They are
tenant-owned and require policies.

    audit_dispatches
    feedback
    hazard_assessments
    hazard_capas
    hazard_rca_entries
    hazard_rca_factors
    invites
    psoe_findings

Status: DEFERRED to Step 2.

Reason: the current identity model (Firebase) does not match
the live policy model (Supabase GoTrue claims). Any policy
written now would either be bypassed by the owner connection,
or expect GoTrue claims that Firebase does not present.

Writing non-enforcing policies would create false assurance.
The correct fix is to rewrite the RLS model against the
Firebase claim path, in Step 2, alongside the membership
model.

Interim protection: the application layer enforces tenant
isolation (WHERE tenant_id = <session tenant>). No live
cross-tenant exposure has been identified for these tables.

### audit_dispatches — special note

Unlike the other seven deferred tables, audit_dispatches has
a live tenant-facing read endpoint:
    GET /api/v1/tenants/sms/audit-logs
    backend/app/api/v1/tenant_reports.py:146-155
    Uses get_tenant_user; reads via list_tenant_dispatches().

The endpoint's tenant scoping is enforced by application
code. A read-only verification of that scoping is part of
this item (Section 3).

### Verification of tenant scoping (2026-10-09)

- Endpoint: `GET /api/v1/tenants/sms/audit-logs`
  (`api/v1/tenant_reports.py:146-155`; router prefix `/sms`,
  mounted under `v1_router` at `/api/v1/tenants`).
- Auth dependency: `get_tenant_user`.
- Tenant source: session — `tenant_id = user["tenant_id"]`
  (`user` resolved by `get_current_user` from the Firebase ID
  token claims). No caller-supplied tenant parameter.
- Filter: `list_tenant_dispatches(tenant_id, ...)`
  (`repositories/audit_repo.py:245-260`) applies
  `where = [AuditDispatch.tenant_id == tenant_id]`; `status`
  is the only optional extra filter.
- Bypass check: **none found for non-cross-tenant callers.**
  The only other reader of dispatch rows is
  `list_recent_dispatches()` (no tenant filter), exposed solely
  at `GET /api/v1/state-risk/audit-logs`
  (`api/v1/state_risk.py:146-155`), which is gated by
  `get_caan_user` (a cross-tenant role by design). A tenant
  caller cannot reach the cross-tenant reader; the
  tenant-facing endpoint is bound to the session tenant.

## 3. RLS bypass — full statement

The database layer does not enforce RLS on the app path.
Two reasons:

    1. The backend connects as the table owner (postgres),
       and RLS is not forced (rls_forced=false).
    2. The live policies read Supabase GoTrue claims
       (auth.jwt(), auth.uid(), app.current_tenant) that
       the Firebase app path does not present.

Either reason alone would prevent enforcement. Both are
present.

See docs/step1/rls_bypass_finding.md for the canonical
statement of the RLS bypass (owner connection + Firebase vs
GoTrue claim mismatch). The summary above is retained for
local reading; the canonical record is the finding document.

## 4. What is enforced, honestly

- Database layer: no RLS enforcement on the app path.
- Application layer: tenant isolation is enforced by
  query filters (WHERE tenant_id = <session tenant>) at
  the service layer.
- Evidence: items 1A.2, 1A.3, 1A.7, 1A.8 verified that
  the app-layer isolation works correctly.

## 6. Classification correction (2026-10-09)

The original 1B.2 draft classified `audit_dispatches` as platform.
That was wrong: the live schema has `audit_dispatches.tenant_id`
(text), it is written per-tenant (`record_tenant_dispatch_intent`,
`workers/tenant_scheduler.py:108`) and read per-tenant
(`list_tenant_dispatches`) via the tenant-facing endpoint above.
SME ruling: it is **tenant-owned** and moves to the deferred list
(Section 2). Platform exemptions are `dead_letter_queue` and
`sms_dispatches` only.
