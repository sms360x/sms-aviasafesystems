## 1. Validation results

- **Registers with period structure:** `hazards` (`created_at`, `status`,
  `tenant_id`, `is_demo`), `reports` (VSR/MOR, `created_at`/`occurrence_date`,
  `report_type`), and `sram_risk_register` (`tolerability_current`, `status`,
  `updated_at`) all carry a time column and a countable attribute. CANs/CAPs and
  SPI values exist but are less directly countable per period.
- **Existing analytics:** `metrics_service.py` is the convention — a **stateless
  pure calculation service** ("No I/O, no side effects, easily testable") whose
  methods take plain dicts and return computed results; it already carries
  `"forecast": None` / `"prediction": None` placeholder slots.
  `aggregation_service.py` (industry aggregation), `dashboard_service.py`,
  `state_risk_service.py`, `ae_kpi_service.py`, `nhrc_service.py` compute
  retrospective measures over periods.
- **Forward-looking output:** **none.** Every existing analytics method is
  retrospective (counts, averages, distributions, trends-to-date). No projection
  exists. This is the finding.
- **Where it lives:** new service file `backend/app/services/predictive_service.py`
  (the convention already has many `*_service.py` modules under
  `backend/app/services/`); the projection arithmetic is a pure, stateless
  function following `metrics_service`.
- **Test style:** hermetic/pure tests (`test_metrics_service.py`) and
  monkeypatched register reads (`test_report_cross_tenant_access.py`).

**Proposal (adopted):**
- Function: `PredictiveService(tenant_id).project_open_hazards(periods_back=6, periods_ahead=1, as_of=None)`
- Input: register `hazards` for the tenant + a historical period window.
- Output: `{periods_ahead, projected_open_count, source_periods, ...}`.
- Register read: `hazards` (tenant-scoped, demo-scoped).

The `occurrences`/VSR-MOR alternative was considered; `hazards` was chosen
because it is the core register, has a clean `status` field, and the
open-count series is directly defensible and simple to test.

## 2. Interface

### Function

```python
PredictiveService(tenant_id: str).project_open_hazards(
    periods_back: int = 6,
    periods_ahead: int = 1,
    as_of: Optional[datetime] = None,
) -> dict
```

Pure helper (no I/O): `_project_counts(counts: Sequence[int], periods_ahead: int = 1) -> {"method": str, "projected": List[Optional[int]]}`.

### Register read

`hazards` only, tenant-scoped and demo-scoped:

```python
pg.fetch_all(Hazard, where=[Hazard.tenant_id == tenant_uuid(tenant_id),
                            Hazard.is_demo == demo_scope()])
```

A hazard counts as **open** when its `status` (uppercased) is not in
`{"CLOSED", "VERIFIED_CLOSED"}`.

### Output shape (stable keys)

| Key | Type | Meaning |
|---|---|---|
| `tenant_id` | str | caller's tenant slug |
| `register` | str | `"hazards"` |
| `measure` | str | `"open_hazards"` |
| `period` | str | `"month"` |
| `method` | str | `"no_data"` \| `"constant"` \| `"linear_trend"` |
| `periods_back` | int | historical months read |
| `periods_ahead` | int | months projected |
| `source_periods` | list | `[{period: "YYYY-MM", count: int}]`, oldest→newest |
| `projected_open_count` | int \| None | next-period value (convenience) |
| `projected` | list | `[{period: "YYYY-MM", count: int\|None}]` |
| `limitations` | str | method limits (Step 4 note) |
| `stronger_method` | str | how to improve (Step 4) |

### Method

Arithmetic only. For the count series of length `n`:

- `n == 0` → `no_data` (projected `None`).
- `n == 1` → `constant` (that count repeated).
- `n >= 2` → `linear_trend`: least-squares slope/intercept over index `0..n-1`,
  extrapolated to the next `periods_ahead` periods, clamped at 0 and rounded to
  the nearest integer.

No ML, no statistics libraries, no external dependencies.

### Limitations / what would improve it (Step 4)

Simple least-squares linear extrapolation of a short monthly series; assumes
the near-term trend continues; ignores seasonality, reporting-rate changes,
backlog dynamics, and per-category structure; bounded at zero. It is a planning
indicator, not a decision. Step 4: seasonal/ARIMA on longer history, separate
new-occurrence inflow from closure outflow, project per taxonomy category with
confidence intervals, and normalise by leading indicators (flight hours).

## 6. Conclusion

The service satisfies the Step 1 acceptance bar: it reads from an existing
register only (`hazards`), adds no new data sources, no ML, and no external
dependencies; it produces a forward-looking output by simple arithmetic
(least-squares linear trend); it has a defined interface (input = register +
period window; output = the documented structure above); it has a passing unit
test on a fixed input producing the expected output; and it is documented here.
It is not wired to any endpoint or UI (by instruction).
