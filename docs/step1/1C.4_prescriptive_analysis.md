## 1. Validation results

- **1C.3 pattern** (`predictive_service.py`) is the convention to match: a
  tenant-scoped service whose rule arithmetic is a **pure, stateless function**
  (`_project_counts` there; `_evaluate_hazard` here), with the service method
  only fetching the register and shaping a documented output.
- **Candidate registers/rules:**
  - CAN/CAP `target_completion_date` in the past → **already surfaced**:
    `escalation_worker.check_overdue_cans` marks CAPs "Overdue",
    `routes/scheduled_jobs.py` emails overdue CAPs, `routes/dashboard.py`
    surfaces EIP/overdue CAP rows and `overdue_count`, and
    `routes/admin.py` runs the overdue scan. Using this rule would **duplicate
    an existing dashboard alert** (no new value).
  - Hazards with NULL/unassessed tolerability → partly surfaced as an
    `UNASSESSED` count on the CAAN state dashboard (`dashboard_service.py:702-703`)
    and in `state_risk_service.py`.
  - **Open hazard with no corrective action after N days** → **not** surfaced as
    a KPI (the dashboard tracks overdue CAPs, which require a CAN/CAP to exist
    already; a hazard with no corrective action is a pre-CAN process gap).
  - Hazard review overdue (`follow_up_date` past) → not surfaced.
- **Most defensible / simplest to test:** `hazards` (single register, clean
  `status`/`corrective_action_flag`/`follow_up_date`/`created_at`/`priority`
  fields), matching the 1C.3 register.

**Proposal (adopted):**
- Function: `PrescriptiveService(tenant_id).recommend_hazard_actions(as_of=None, no_action_days=30) -> list[dict]`
- Input: register `hazards` for the tenant + `as_of` + threshold.
- Output: an ordered list of recommendation dicts (see §3).
- Register read: `hazards` (tenant-scoped, demo-scoped).
- Rules: `corrective_action_missing`, `review_overdue`.

## 2. Interface

### Function

```python
PrescriptiveService(tenant_id: str).recommend_hazard_actions(
    as_of: Optional[date | datetime] = None,
    no_action_days: int = 30,
) -> list[dict]
```

Pure rule function (no I/O): `_evaluate_hazard(row: dict, as_of: datetime, no_action_days: int) -> list[dict]`.

### Register read

`hazards` only, tenant-scoped and demo-scoped:

```python
pg.fetch_all(Hazard, where=[Hazard.tenant_id == tenant_uuid(tenant_id),
                            Hazard.is_demo == demo_scope()])
```

A hazard is **open** when its `status` (uppercased) is not in
`{"CLOSED", "VERIFIED_CLOSED"}`.

### Input shape

| Input | Type | Meaning |
|---|---|---|
| `as_of` | date \| datetime \| None | reference instant; defaults to now (UTC); pass a fixed value for reproducible output |
| `no_action_days` | int (>= 1) | threshold used by the rules |

### Output shape (list, ordered)

Each item:

| Key | Type | Meaning |
|---|---|---|
| `action` | str | short action label |
| `reason` | str | rule name that fired |
| `subject` | dict | `{"id": <hazard_id>, "type": "hazard"}` |
| `severity` | str | `"low"` \| `"medium"` \| `"high"` |
| `due_by` | str \| None | `"YYYY-MM-DD"` or `None` |

Ordering: by severity (high → medium → low), then action label, then subject id
(deterministic). A hazard may fire more than one rule.

## 3. Rule list

| Name | Condition | Action | Severity | `due_by` |
|---|---|---|---|---|
| `corrective_action_missing` | open **and** `corrective_action_flag` false **and** `as_of - created_at >= no_action_days` | "Raise a corrective action (CAN)" | `high` if `priority == "H"` or age `>= 2*no_action_days`, else `medium` | `None` |
| `review_overdue` | open **and** `follow_up_date` set **and** `follow_up_date < as_of` | "Complete the overdue hazard review" | `high` if overdue days `>= no_action_days`, else `medium` | the `follow_up_date` |

The rules are a module-level `RULES` tuple in `prescriptive_service.py` (the
single documented source of truth) and are deterministic; no ML and no
heuristics beyond these conditions.

## 4. Limitations / what would improve it (Step 4)

Deterministic threshold rules over the hazard register only. They are process
prompts, not safety judgements: thresholds are fixed (no per-tenant or
per-category tuning); they read no downstream registers (CAN/CAP/SRM status);
and they do not rank by risk magnitude beyond the hazard priority. Step 4:
weight recommendations by risk severity/probability and safety outcome, join
CAN/CAP/SRM status so a rule fires only when the downstream action is genuinely
absent, make thresholds tenant-configurable, and suppress/merge duplicate
prompts per hazard.

## 7. Conclusion

The function satisfies the Step 1 acceptance bar: it reads from an existing
register only (`hazards`), adds no new data sources, no ML, and no external
dependencies; it produces recommended actions derived from a small, documented,
deterministic rule list; it has a defined interface (input = register + period
context; output = the documented structure above); it has passing unit tests on
fixed input producing expected output (per-rule isolation, no-fire, isolation,
shape); and it is documented here. It does not duplicate an existing dashboard
alert (overdue CAPs/EIP and the UNASSESSED count were deliberately avoided).
It is not wired to any endpoint or UI (by instruction).
