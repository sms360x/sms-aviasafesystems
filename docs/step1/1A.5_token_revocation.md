# Step 1 — Evidence 1A.5: Firebase token revocation

PHASE: 1A
ITEM: 1A.5 — Verify token revocation and pin it with a regression test
STATUS: closed (M1 confirmed enforced; regression test added)
DATE: 2026-10-09
BRANCH: step1-audit-readiness

## Verification result — the site with `check_revoked`

The single token-verification site is:

- `backend/app/firebase.py:105` — `verify_firebase_token()` calls
  `auth.verify_id_token(token, check_revoked=True)`.

The SDK default is `check_revoked=False`. The flag was briefly disabled in
`a1b422a` ("disable check_revoked to avoid clock skew issues") and restored by
`6383452` (H1+H2+H3+M1). **Confirmed `check_revoked=True`.**

The function maps the SDK error classes to `None`:

- `ExpiredIdTokenError` -> `None`
- `RevokedIdTokenError` -> `None`
- `InvalidIdTokenError` -> `None`
- any other exception (includes `UserNotFoundError` for a deleted user) -> `None`

## Other token-verification sites (validation 1.5)

There is exactly one place the SDK is invoked. No other module calls
`auth.verify_id_token` / `auth.verify_session_cookie` directly. Every auth
caller routes through `verify_firebase_token`, so `check_revoked=True` is
enforced everywhere:

- `backend/app/middleware/auth.py:124` — `get_current_user` (asyncio auth)
- `backend/app/middleware/rbac_middleware.py:78` — module gate `_user_from_request`
- `backend/app/routes/admin.py:124` — admin debug verify
- `backend/app/routes/auth.py:128` — legacy login/token exchange

No site uses `check_revoked=False`. No new verification path was introduced.

## Test harness

`tests/test_token_revocation.py` (new, 12 tests). The revoked/deleted cases are
simulated at the SDK boundary by monkeypatching
`app.firebase.auth.verify_id_token` to raise the exact exception the SDK raises
with `check_revoked=True` (`RevokedIdTokenError`, and `UserNotFoundError` for a
deleted user — the SDK's `_check_jwt_revoked_or_disabled` calls `get_user()`
after verifying the JWT). No new harness or dependency was needed.

## Test list

Core pin (fails if `check_revoked` is ever flipped to `False` or dropped):

- `test_verifier_passes_check_revoked_true` — asserts the call carries
  `check_revoked=True`.

Accepted:

- `test_valid_non_revoked_token_accepted` — verifier returns the decoded claims.
- `test_valid_token_accepted_over_http` — `GET /api/v1/nhrc/mapping-rules` with a
  valid Bearer token -> **200**.

Rejected — verifier maps the SDK error to `None` (parametrized, 4):

- `test_rejected_token_returns_none[revoked]` — `RevokedIdTokenError`.
- `test_rejected_token_returns_none[deleted_user]` — `UserNotFoundError`.
- `test_rejected_token_returns_none[expired]` — `ExpiredIdTokenError`.
- `test_rejected_token_returns_none[malformed]` — `InvalidIdTokenError`.

Rejected — HTTP surface answers **401** (parametrized, 4):

- `test_rejected_token_gets_401_over_http[revoked|deleted_user|expired|malformed]`
  — same protected route -> **401** with `WWW-Authenticate: Bearer`.

Boundary:

- `test_missing_token_rejected_over_http` — no header -> **401/403** (FastAPI
  `HTTPBearer` auto-rejects with 403; both are rejections).

## Conclusion

**M1 is closed by evidence.** Token revocation is enforced at the single
verification site with `check_revoked=True`, every caller routes through it, and
`test_token_revocation.py` pins the flag plus the revoked / deleted-user /
expired / malformed rejection behaviour so a regression fails the suite.

## Residuals

- The clock-skew note from `a1b422a` remains: `verify_firebase_token` does not
  pass a `clock_skew_seconds` tolerance. Re-enabling revocation checked with the
  strict default is the intended M1 posture; this is recorded for awareness, not
  reverted here.
- One API surface is covered end-to-end (`/api/v1/nhrc/mapping-rules`); the other
  call sites share the same `get_current_user` / `verify_firebase_token` code
  path, so no separate per-route revocation test is required.
