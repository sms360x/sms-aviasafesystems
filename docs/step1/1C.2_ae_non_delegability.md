# 1C.2 — AE Non-Delegability (CAAN SRM Manual §2.3.3)

PHASE: 1C
ITEM: 1C.2 — verify and enforce AE non-delegability; add regression tests
STATUS: complete (enforcement already present; tests added; no code change)
DATE: 2026-10-10
BRANCH: step1-audit-readiness

The Accountable Executive's signature on a risk acceptance cannot be delegated
(CAAN SRM Manual §2.3.3). Enforcement was found to be **already present** on the
risk-acceptance path, so per instruction Section 2.1 no production code was
changed; regression tests were added to pin the rule. One adjacent defect
(hazard-closure gating) is recorded as a residual, not fixed here.

## 1. Validation results

### 1.1 `backend/app/services/sram_service.py`

- `process_sign_acceptance` (Signature 1 — process conformance, Module B §17):
  records `process_by` + `process_signed_at` from the **session** user
  (`_resolve_user_uuid(user)`, resolved by uid/email). No identity comes from a
  request parameter. It has no role gate (any tenant user may provide the
  process signature; acceptance is what is gated).
- `accept_risk` (Signature 2):
  - Requires the process signature first (`process_by`/`process_signed_at`),
    else 403.
  - Grades the required role on the **INITIAL** tolerability via
    `AUTHORITY_ROLES` (`:51-55`):
    - `Intolerable` → `{ACCOUNTABLE_EXECUTIVE}`
    - `Tolerable` → `{SAFETY_OFFICER, OFFICER, TENANT_ADMIN, AIRLINE_ADMIN}`
    - `Acceptable` → adds `SAG_MEMBER`
  - Checks `acting_role = user["role"]` (the **session** role) against the
    required set, else 403 (`:583-591`).
  - Sets `accepted_by = _resolve_user_uuid(user)` — the **session** user's
    `users.id` — and snapshots `initial_authority`/`resultant_authority`.
  - There is **no override/delegation branch**.

### 1.2 `backend/app/services/can_cap_service.py` + `routes/can_cap.py`

- `CanCapService._ae_decide_async` (`:1090-1100`) requires
  `user["role"] == "ACCOUNTABLE_EXECUTIVE"` (exact), else `PermissionError`; the
  decision is immutable after the first call; `ae_signature.signed_by` is the
  session email/uid.
- `POST /api/v1/cans/caps/{cap_id}/ae-decision` (`routes/can_cap.py:351-390`)
  additionally gate-checks the exact AE role and writes a `CAP_AE_DECISION`
  audit record. A non-AE cannot trigger an AE decision.

### 1.3 `backend/app/api/v1/endpoints/sram.py:242` (`accept_risk`)

- Uses `Depends(get_current_user)` and delegates authority/tier enforcement to
  `sram_service.accept_risk`. Scope is `_resolve_scope(user)` (the caller's own
  tenant; the endpoint takes no tenant parameter). Cross-tenant roles with no
  tenant are rejected before the service (403).

### 1.4 `backend/app/routes/verification.py`

- `POST /hazards/{hazard_id}/closure` uses `Depends(get_accountable_executive)`
  (`:76`). **Defect:** `middleware/auth.get_accountable_executive`
  (`:254-267`) admits `settings.CROSS_TENANT_ROLES` **or** `"AIRLINE_ADMIN"` — it
  does **not** admit the canonical `ACCOUNTABLE_EXECUTIVE` role. So hazard
  closure is not truly AE-gated (legacy Safety Manager + regulators pass; the
  real AE would be denied). `approved_by` is still session-derived. This is a
  **closure** sign-off, not risk acceptance, and fixing it is a role-model
  decision (Section 2.4 forbids that here) — recorded as residual.

### 1.5 AE decision flow — identity source

All AE-signing paths derive identity from the **session** (`user["role"]`,
`user["email"]`/`uid`): SRAM `accept_risk`, CAP `ae-decision`, and hazard
`closure`. No endpoint accepts a signer identity as a request parameter. The
demo path (`routes/demo.py` `/session/decision`) additionally requires
`body.email == session.email` and writes only to isolated demo overlays.

### 1.6 Role constants

- `settings.ROLE_ACCOUNTABLE_EXECUTIVE = "ACCOUNTABLE_EXECUTIVE"`;
  `ACCOUNTABLE_EXECUTIVE_ROLES = ["ACCOUNTABLE_EXECUTIVE"]`. No legacy alias or
  dual-accept shim for the AE (comment: "new literal, no legacy alias").
- `sram_service.AUTHORITY_ROLES` keys on literal role strings.
- **Cross-tenant roles are not permitted to act as the AE** (not in any
  `AUTHORITY_ROLES` set; the CAP path requires the exact AE role; scope rejects
  tenantless cross-tenant callers).
- Inconsistency noted: `get_accountable_executive` (1.4) is the one place that
  neither requires nor recognises the canonical AE role.

### 1.7 Existing tests

- `backend/tests/test_ae_decision_api.py` — CAP AE role gating, EIP, immutability,
  decision PDF.
- `backend/tests/test_hazard_service.py::test_authority_tier_enforced_and_snapshot`
  and `::test_two_signature_workflow_accepts_after_process_sign` — authority-tier

## 2. The rule as enforced, and where

| Path | Enforced by | Identity source |
|---|---|---|
| Risk acceptance (Intolerable) | `sram_service.accept_risk` authority tier → `{ACCOUNTABLE_EXECUTIVE}` | session (`accepted_by = _resolve_user_uuid(user)`) |
| Risk acceptance (Tolerable/Acceptable) | same tier (Safety roles — lower tier, permitted by design) | session |
| CAP AE terminal decision | `CanCapService._ae_decide_async` + route gate + `CAP_AE_DECISION` audit | session |
| Hazard closure (residual) | `get_accountable_executive` — **incorrect** (admits AIRLINE_ADMIN/cross-tenant, excludes the AE) | session |

## 3. Code change

**None.** Enforcement of AE non-delegability on risk acceptance is present at the

defect is out of scope (role-model change forbidden by Section 2.4) and recorded

## 6. Conclusion

AE non-delegability for **risk acceptance** (CAAN SRM Manual §2.3.3) **is enforced
by the code**: only the `ACCOUNTABLE_EXECUTIVE` may accept an Intolerable risk,
the accepting identity is the session user, no signer identity is accepted from a
request parameter, cross-tenant roles are refused, and the CAP AE terminal
decision is likewise AE-only and audited. No production code change was needed;
regression tests now pin the rule.

  admits `AIRLINE_ADMIN`/cross-tenant and excludes the canonical AE role
  (`routes/verification.py:76`). Not fixed here (role-model change; Section 2.4).
  Record for Step 2 role-model reconciliation.
- **No audit on risk acceptance** — `sram_service.accept_risk` (and its route) do
  not call `log_audit`; only the CAP AE decision path writes an audit record.
  Recorded; not in scope for non-delegability.
- **No override path exists**, so there is nothing to audit for overrides; if an
  override is ever introduced it must log reason + actor.
